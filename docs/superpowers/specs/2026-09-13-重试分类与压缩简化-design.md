# 重试分类间隔 + 压缩简化设计

日期：2026-09-13
状态：待用户审阅
前序：`2026-08-24-retry429-design.md`、`2026-08-27-瞬时错误长重试增强-design.md`、`2026-09-02-网络错误长重试-design.md`、`2026-08-23-上下文压缩稳健化-design.md`

> 修订（2026-09-13 fix wave，用户已确认）：压缩切割单位由"完整回合链"改为"**原子组**"，并**至少保留最近 8 个原子组**（写死）。原因：实测一个任务自主调用 48 轮即超窗、上百轮常见，而旧链粒度下整条任务链只能"全压或全不压"——全压会丢失当前任务状态（模型重复劳动/答非所问），不压则压缩空转。原子组切割可只压缩早期工具往返、保留最近若干组让模型接着干活（滚动压缩）。同时修评审缺陷：旧摘要输入由"只取第一条"改为拼接全部 summary 消息，历史遗留多条摘要不再丢信息。

## 背景与问题

### 重试

现状（三处重试循环：主循环 `AgentLoop`、子 agent `SubAgentLoop`、压缩通道 `ContextManager.callLlm`）：

- 长重试固定 5s/次、墙钟 20 分钟，覆盖 429 / 500 / 502 / 超时 / 可恢复网络错误；
- 503/504 等其他 5xx 只走"短重试 1 次（0.5s）"；
- HTTP 200 但响应体为 null（"空响应"）标记 `retryable=false`，一次即报错；
- 压缩通道无重试：LLM 调用失败即静默降级（分段递归、部分成功、全部失败原样返回）。

问题：500 类失败多因服务器重启等不稳定因素，5s 重试几乎必然再失败（浪费次数）；空响应明明可恢复却不重试；20 分钟墙钟过长；压缩通道失败后无补救，上下文卡在高位。

### 压缩

现状 `ContextManager`：阈值/保留条数来自模型配置（`compressThreshold`/`keepRecentMessages`），算法为"保留区占比动态缩小 + 失败按 token 二分递归降级 + 摘要前缀合并"，约 250 行，复杂且难验证。

问题：递归降级路径难测（分段/前缀/部分成功组合多）、失败静默返回原样让用户以为"无可压缩"、保留条数配置对用户无意义。

## 需求（已与用户逐条确认）

1. 重试间隔按错误类别区分：429/超时类 = 5s；500 类 = 30s；**等待时长由最近一次失败的类别决定**
2. 503/504 等其他 5xx 纳入 500 类（30s 长重试），不再只短重试 1 次
3. 空响应（HTTP 200 但响应体 null）改为按 500 类（30s）长重试
4. 墙钟总时长 20 分钟改为 12 分钟（主循环 / 子 agent / 压缩通道一致）
5. 压缩通道按同一重试规则重试；**失败不再降级**，耗尽重试后报错并**中止本轮，不发送请求**
6. 压缩递归逻辑整体去除
7. `compressThreshold`、`keepRecentMessages` 从模型配置与设置页移除；代码写死阈值 **0.65**，仅保留 `maxContextTokens`
8. 压缩算法：切割单位为**原子组**（`assistant(tool_calls)+其后的 tool 结果` 捆为一组；普通 user / assistant 各自一组），从最早组逐组累加 token，累计首次达到 `maxContextTokens×0.65×0.8` 时截断，之前的组整体压缩；**至少保留最近 8 个原子组**（写死）；最小组仍保证 tool_call↔tool 配对不被切断（200k 模型：130k 触发 → 压掉 ≈104k → 保留 ≈26k 原文 + 摘要）
9. 摘要长度固定 **5000 字**（替换现有"3000 字以内"；不做动态计算）
10. 去掉 Esc 停止对话快捷键（防误触）
11. 新建模型上下文默认值 200k；内置 `createDeepseek`/`createQwen` 的 `displayName`/`modelName` 简化为 `deepseek`/`qwen`（不再写具体型号）

## 非目标

- 不改首增量看门狗阈值（60s）、连接/读超时（30s/300s）、零增量闸门、用户中断优先等既有前提
- 不做运行期可视化配置（阈值/间隔不进 `config.properties`）
- 不改 `config_deepseek.properties`/`config_qwen.properties` 之外的资源（两个文件中的 `context.compressThreshold`/`context.keepRecentMessages` 行顺手删除，无代码读取）
- 不改纯文本回复、工具调用回合的正常路径
- 历史 spec/plan 文档中的旧数值不回改

## 设计

### §1 重试策略

#### 1.1 错误分类与间隔

| 类别 | 等待间隔 | 覆盖错误 |
|---|---|---|
| SHORT | **5s** | 429（RATE_LIMIT）、超时（TIMEOUT：60s 首增量看门狗 / 30s 连接 / 300s 读超时）、可恢复网络错误（NETWORK 且 `retryable`） |
| LONG | **30s** | 500、502、**503/504 及其他 5xx（新增）**、**空响应（新增）** |

墙钟总时长：**12 分钟**（`12 * 60 * 1000L`，含每次请求自身耗时与等待，与现状墙钟口径一致）。

#### 1.2 实现

- `RetryPolicy` 精简为 `(shortDelayMs=5000, longDelayMs=30000, maxTotalMs=12min)`，方法：
  - `long delayMs(Kind kind)`
  - `boolean isExhausted(long elapsedMs)`（不变）
  - `static boolean isTransient(LlmException e)`、`static Kind kindOf(LlmException e)`——把现有 `AgentLoop.isTransientError` 与 `SubAgentLoop.isTransientError` 的重复判定收敛到一处，供主循环/子 agent/压缩重试三方共用
- 分类映射（`kindOf`）：
  - `RATE_LIMIT`、`TIMEOUT`、`NETWORK(retryable)` → SHORT
  - `EMPTY_RESPONSE`（新增类型）、`httpCode >= 500`（500/502/503/504 及其他 5xx 一律计入）→ LONG
- `LlmException` 新增 `Type.EMPTY_RESPONSE`：`DeepSeekClient` 中 `response.body() == null` 由 `OTHER/retryable=false` 改为 `EMPTY_RESPONSE/retryable=true`；全仓库 `Type` 引用处（`RetryProgress.from/tag` 标签"空响应"、判定分支、测试替身）补全新枚举值；
- 每次重试等待时长由**最近一次失败**决定：
  ```java
  LlmException last = e;
  while (true) {
      attempts++;
      long delay = retryPolicy.delayMs(RetryPolicy.kindOf(last));
      ui.onRetryProgress(RetryProgress.from(attempts, last, delay)); // 携带下次等待时长
      if (!sleepWithInterruptCheck(delay)) break;                    // 用户中断
      ...
  }
  ```
- 前缀 `if (isTransientError(e) && noOutputYet(...))` 改用 `RetryPolicy.isTransient(e)`；进入条件不变（零增量闸门、中断优先）。
- **短重试分支（`e.retryable && retries < 1`，0.5s/2s）保留为兜底**：503/504 纳入后该分支实际不可达，但保留以防未来新增"可重试但未分类"错误；注释注明现状几乎不触发。
- **超长首增量等已吐字**路径不重试（零增量闸门不变）。

#### 1.3 指示器

`RetryProgress` 增加 `nextDelayMs` 字段与工厂重载；`RunningIndicator.retryText` 追加"，约 N 秒后重试"（N 由毫秒向上取整到秒；`nextDelayMs<=0` 时省略）。30s 静默等待用户可见。

#### 1.4 文案

- 耗尽文案：`<标签> 重试了 N 次，持续 12 分钟仍失败，已停止重试`（现状 `elapsed/60000` 取整，不变）
- 子 agent 耗尽文案同步。

### §2 上下文压缩

#### 2.1 配置精简

| 文件 | 改动 |
|---|---|
| `ModelConfig` | 删除 `compressThreshold`、`keepRecentMessages` 字段（含 `copy()`） |
| `ModelManager` | `createDeepseek`/`createQwen` 不再赋值；`update` 不再复制 |
| `SettingsDialog` | 模型表单删除 `compressThreshold`/`keepRecentMessages` 两行输入与回填 |
| `SessionManager` | 3 处 `new ContextManager(...)`/`cm.update(...)` 改新签名 |
| `ContextManager` | 构造签名 `(int maxContextTokens, LlmClient llm, int systemTokens)`；`update(int maxContextTokens)`；`threshold()` 返回常量 `0.65` |

兼容性：旧 `model.json` 中多出的两个字段被 gson 忽略，不报错、无需迁移；编辑旧模型保存后两字段自然消失。
顺手清理：`src/resource/config_deepseek.properties`、`config_qwen.properties` 中的 `context.compressThreshold`/`context.keepRecentMessages` 行（全仓库无代码读取）。

#### 2.2 常量

```java
static final double THRESHOLD = 0.65;      // 触发阈值（写死，不进配置）
static final double COMPRESS_RATIO = 0.8;  // 触发量中要压缩的比例
static final int SUMMARY_MAX_CHARS = 5000; // 摘要上限 5000 字（字符口径，写入压缩提示词）
static final int KEEP_RECENT_GROUPS = 8;   // 至少保留的最近原子组数（写死，不进配置）
```

触发点 `maxContextTokens × 0.65`；压缩量 `maxContextTokens × 0.65 × 0.8`（200k → 104k）。

#### 2.3 新算法（替换递归实现）

```java
public List<Message> compress(List<Message> messages) throws LlmException
```

1. `groups = chunkGroups(messages)`：**原子组**是最小可切割单位——有工具调用的 `assistant` 与其后的 `tool` 结果捆成一组（`tool_call↔tool` 配对不切断，否则接口 400）；普通 user / assistant（无工具调用）各自一组；summary/pinned/system 跳过（不入组、不参与压缩）
2. 空组或组数 ≤ `KEEP_RECENT_GROUPS`（8）→ 返回原 `messages`（语义：暂无可压缩，不抛错、不调 LLM；"至少保留最近 8 组"是硬性约束）
3. 从最早组逐组累加 token，求要压缩的组数 `take`：累计到**首次 ≥ compressTokens** 的组数即 `take`（含该组，保证压缩量 ≥ 80%）；上限 `maxTake = 组数 − 8`（保证至少保留最近 8 组）；有可压缩组时 `take ≥ 1`（保证推进）
4. 压缩输入 = 既有摘要文本（`messages` 中**全部** `summary==true` 消息按顺序拼接，置前；兼容历史遗留多条摘要的会话）+ `groups[0..take)` 的批次文本（沿用 `buildBatch` 格式）
5. 单次 LLM 调用（非流式 `completeChat`，system 提示词改为"…5000 字以内"）；**空摘要视为失败**，抛 `EMPTY_RESPONSE`
6. 成功 → 结果结构不变：`[system...] + [新摘要] + [pinned...] + groups[take..]`（旧摘要由新摘要取代；新摘要输入含全部旧摘要，信息不丢）
7. 失败 → 抛 `LlmException`（不再降级、不再部分成功）

删除成员：`SEGMENT_MIN`、`KEEP_MIN`、`KEEP_RATIO`、`SegResult`、`compressChains`、`splitByTokens`、`splitOversizedChains`、`splitChainByMessages`、`takeChains`、`computeTake`、`callLlm`（静默降级版）、`lastCompressAttempted`（语义由"是否抛异常"取代）。

`shouldCompress` 判定不变（`estimate >= maxContextTokens × 0.65`，仍含 systemTokens）。

#### 2.4 压缩重试编排（AgentLoop）

- 新增 `private List<Message> compressWithRetry() throws InterruptedException`（或返回成功标志）：
  - 重试条件：`RetryPolicy.isTransient(e)`；不可重试错误（401/400/DNS 等）直接失败
  - 间隔按 `kindOf`（429/超时 5s、500 类/空响应 30s）、墙钟 12 分钟、`sleepWithInterruptCheck` 可被"停止"中断
  - 指示器：`onRetryProgress(attempt, e, delay)`；重试成功/失败后复位
  - `ui.onCompressingChanged(true/false)` 包裹全程
- 自动压缩（`runUserTurn` 前置）与手动 `/compact`（`compactNow`）共用该方法；失败文案按调用方区分——自动「自动压缩失败：…；本轮已停止」，手动「压缩失败：…」（不带"自动"字样）
- **耗尽/不可重试 → `ui.onError("自动压缩失败：<原因>；已重试 N 次持续 X 分钟。本轮已停止，可稍后重试或新建会话")` 并中止本轮，不发送请求**（手动路径同处报错，前缀为「压缩失败：」）
- 成功 → 沿用 `onWarning("自动压缩已完成，上下文降低至 X%")`
- 用户中断（停止）→ 静默结束本轮（与现状一致）

## 风险与兼容性

- **12 分钟 × 30s**：LONG 类最多约 24 次尝试，SHORT 类约 140 次；中途类别切换按最近一次计算
- **空响应长重试**：模型名/端点配错会白等 12 分钟（表现为持续"重试第 N 次"），比现状慢失败；属用户明确选择
- **短重试兜底**：保留但几乎不可达，不改变现有行为
- **压缩信息损失**：去递归后一次性压缩量大（104k），摘要需承载较多信息；固定 5000 字上限可能截断超长历史（用户明确要求固定值）
- **压缩边界**：原子组为最小单位，`assistant(tool_calls)↔tool` 配对不切断；**至少保留最近 8 组**（硬性），当前任务进行中的上下文不会被压光；48 轮以上长任务可滚动压缩（早期工具往返进摘要，最近 8 组原文保留）；组数 ≤ 8 时暂不压缩（本轮照发，超窗由服务端报错兜底）；`take` 含首次达到预算的组，压缩后大小 ≈（200k−104k）+ 摘要
- **多条旧摘要**：历史遗留 ≥2 条 summary 的会话，压缩输入拼接全部摘要文本，不再只取首条
- **旧 model.json**：多出字段被忽略；用户自定义的 0.8/50 会被写死 0.65 取代（用户明确要求）
- **编译期影响面**：`ModelConfig` 字段删除会牵连所有引用（已列全：ModelManager/SettingsDialog/SessionManager/ContextManager 及测试）
