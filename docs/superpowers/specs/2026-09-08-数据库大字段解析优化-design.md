# 数据库大字段解析优化设计

日期：2026-09-08
状态：待评审

## 1. 背景与问题

mysql / oracle / postgreSQL 只读查询工具（DbTool → DbExecutor → MarkdownTable）对大字段
（CLOB / TEXT / LONGTEXT / JSON / XML / 长 VARCHAR 等）的内容一律按 `CELL_MAX=120` 截断，
且截断仅追加一个省略号"…"，**不告知模型内容不完整**。

实际使用中大部分分析需求包含大字段解析（如读 JSON 配置、解析日志/协议文本），当前行为导致：

1. 120 字符内看不到任何实质内容，模型拿不到解析素材；
2. 模型误以为截断后的片段就是字段全貌（无截断提示），不会主动寻求更多内容，解析结论失真。

## 2. 目标与非目标

### 目标

- 概览查询保持表格紧凑（行数/总预算卫生不放松）；
- 模型能够以自然、显式的方式取得目标行的**大字段全文**用于解析；
- 任何被截断的单元格都**显式标注真实长度**，消除"以为取全"的盲区；
- 全文仍超预算时沿用既有"落盘 + Read 路径"兜底。

### 非目标

- 不提高 `CHAR_BUDGET=30000` 总预算（与 Grep/Bash 同口径的上下文卫生约束，不动）；
- 不提高 `MAX_ROWS=100` 行数上限；
- 不做 GUI 层改动（结果呈现形态不变，仍是 Markdown 表格 + 落盘引用）；
- 不做按字段类型识别（不依赖各驱动 `getColumnTypeName` 返回差异，见 §5 判定规则）。

## 3. 方案总览（三层递进）

| 层 | 机制 | 触发 | 改动 |
|---|---|---|---|
| ① 截断透明化 | 被截断单元格后缀标注 `…[完整 N 字符]` | 所有查询默认开启 | MarkdownTable.cell |
| ② 全文模式 | 截断线放宽 120 → 20000/格 | query 可选参数 `full=true` | DbTool / DbExecutor / MarkdownTable |
| ③ 落盘兜底 | 返回总长超 30000 → 头部 + 完整落盘路径 | 自动（现状保留） | 无 |

### 交互闭环（核心场景）

```
模型浏览定位：  query  "SELECT id, title, body FROM t ..."（默认）
                → body 显示 前120字符 + [完整 23,456 字符]     ← 模型知道没取全

模型解析正文：  query  "SELECT body FROM t WHERE id=..."  full=true
                → ≤20000 全文 inline；>20000 → 头部 + 落盘路径，Read 全文
```

## 4. 接口变更

### DbTool（工具 schema）

- query 增加可选布尔参数 `full`，缺省 `false`。
- description 追加说明：
  「大字段（CLOB/TEXT/LONGTEXT/JSON 等）默认截断 120 字符并标注完整长度；
  解析大字段全文时请设 full=true，并将 SQL 限定到少数行/单行（配合 WHERE/LIMIT），
  单个字段最多 inline 20000 字符，超出会自动落盘并给出文件路径。」

### DbExecutor

- `query(DataSourceConfig ds, DbType type, String sql)` → 增加重载/参数 `boolean full`。
- 读取行时按列计算截断线：
  - `full == false`：所有列 120（现状）；
  - `full == true`：所有列 20000（内容不足截断线则原样呈现，行为不变）。
- `listTables` / `describe` 不带 full（元信息场景，不涉及大字段正文）。

### MarkdownTable

- `cell(Object v)` 保留为默认 120 的便捷入口；新增 `cell(Object v, int cellMax)`。
- 截断时返回值追加 `…[完整 N 字符]`（N 为**转义前**原文长度，千分位不分组）。
- 截断位置处理：若末字符是孤立高代理（emoji 代理对被切断），回退一位再追加（对齐
  TruncatedOutput 既有口径）。
- `render` 不需要列级截断线：单元格值由 DbExecutor 在行循环内经 `cell(v, max)` 预处理，
  render 只负责拼接（实现简化：spec 原稿的「render 透传列级截断线」删除）。
- 换行/竖线转义顺序不变（先 `\n`→`<br>`、`|`→`\|`，后截断），标注串本身无竖线/换行。

## 5. 判定规则（刻意简单，无类型依赖）

- 全文模式不按 JDBC 类型/驱动类型名判定大字段，而是**放宽所有列的截断线**：
  - 内容 ≤120：与默认模式输出完全一致（无行为差异）；
  - 内容在 (120, 20000]：全文 inline（这正是"取全文"诉求的区间）；
  - 内容 >20000：截断到 20000 + `[完整 N 字符]` 标注（模型知道还要 Read）。
- 理由：各驱动 `getColumnTypeName` 返回值不统一（Oracle 报 CLOB、MySQL 报 LONGTEXT，
  但动态拼接的长 VARCHAR 也会出现）；放宽上限而非类型判断，行为可预期、零误判，
  且模型显式声明 full=true 已表明意图。

## 6. 边界与错误处理

- `full=true` 且结果集多行/多列均为超长文本：逐格尽量 inline，累计超
  `CHAR_BUDGET=30000` 后由既有 `MarkdownTable.fit` 落盘截断（返回头部+路径），
  行为与现状一致；由 description 引导模型避免该用法。
- 落盘失败 / tmpDir 为 null：fit 既有降级文案不变。
- 标注字符数计入总预算（每截断格约 +20 字符，相对影响可忽略）。
- null 值显示 `NULL`（现状不变）；空串不受截断影响。

## 7. 测试计划

单测（MarkdownTable 为纯函数，可直接断言）：

1. `cell` 不超 120 原样返回；
2. `cell` 超 120 → 前 120 + `…[完整 N 字符]`，N 为原文长度；
3. `cell` 高代理对边界：截断位落在 emoji 中间不产生孤立高代理；
4. `cell(v, 20000)` 20000 内全文返回；
5. `cell(v, 20000)` 20000 内全文返回、超出截断且标注真实长度；
6. 标注按转义前原文长度计（换行多的内容不被 <br> 膨胀虚报）；
7. 高代理边界：截断位落在 emoji 中间不产生孤立高代理；
8. DbTool.fullOf 容错解析（布尔原值/字符串大小写/空白/畸形）；
9. DbTool schema 声明 full 参数；
10. 既有回归：普通查询（无 full）输出与改动前一致，仅截断单元格追加标注。

## 8. 影响与同步

- 无 config.properties / tools.json 变更（不加配置项，full 为每调用参数）。
- README 无功能清单变更（不新增工具）；设计文档本文档留档。
- 涉及文件：`MarkdownTable.java`、`DbExecutor.java`、`DbTool.java` + 单测
  （`MarkdownTableTest` / `DbExecutorTest` 若无则新建）。
