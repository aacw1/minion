# 网络错误纳入长重试 + 墙钟计时改造设计

日期：2026-09-02
状态：待用户审阅（三节设计已获批准并落文档；审阅中追加"DNS 解析失败短路"需求 6）
前序：`2026-08-24-retry429-design.md`、`2026-08-27-瞬时错误长重试增强-design.md`

## 背景与问题

内网模型服务不稳定，已实现 429/500/502 长重试（固定 5s/次、总时长 20 分钟）。本次要解决两件事：

1. **网络类错误不重试**：`TIMEOUT`（连接/读超时）与 `NETWORK`（连接被拒、reset、DNS 失败等）目前只走 `retries < 1` 的快速重试分支——0.5s 退避后重试 1 次即向用户报错。内网抖动场景下这一下基本必然再失败，表现为"发一条消息就红字报错"。
2. **"20 分钟"语义名不副实**：`AgentLoop:482` 的 `waited += delay` 只累加**睡眠时间**，不含每次请求自身耗时。429/500/502 因失败是秒级返回，实际耗时恰好接近 20 分钟，问题被掩盖；一旦把 TIMEOUT（read 上限 300s）纳入，最坏墙钟将达 `239 × 305s ≈ 20 小时`，完全不可接受。

用户预期（本次确认的语义）：网络超时按"单次约 60s + 等 5s"计，20 分钟约重试 19 次。

## 需求

1. `TIMEOUT`、`NETWORK` 进入长重试，与 429/500/502 共用同一策略（固定 5s/次、上限 20 分钟）
2. "20 分钟"改为**墙钟总时长**：从进入重试态起算真实经过时间（含每次请求耗时 + 等待），满 20 分钟停止
3. 网络超时的判定阈值收敛到 60 秒量级，使重试次数符合预期——但**不得误杀正在正常吐字的慢流**
4. 子 agent 与主循环行为一致，互不影响
5. 左下角指示器能正确表达网络类错误（当前无 HTTP 码，会被渲染成 `HTTP 0`）
6. **永久性网络故障快速短路**：域名解析失败（`UnknownHostException`，API 地址写错/本机断网）不进长重试，一次即报错并给出"检查 API 地址"的指向

## 已确认的边界

- 长重试覆盖集合：`RATE_LIMIT`、`TIMEOUT`、`NETWORK`（仅 `retryable==true` 者）、`httpCode==500`、`httpCode==502`
- **仅 `UnknownHostException` 短路**：`ConnectException`（connection refused）与 `SSLException`（TLS 配置错）维持长重试——内网服务重启头几秒必然拒连，重试才是对的；用户确认只短路 DNS 一类
- **503/504 等其他 5xx 不纳入**，维持现状（快速重试 1 次后报错）
- **SSE 已开始吐字后中途断流不纳入**：该路径走 `handler.onError` 回调（`finish=="error"`，`AgentLoop:527`），不经过 `catch LlmException`；纳入需回退 ChatView 已渲染增量与已入列 assistant 消息，代价与收益不匹配，维持现状
- 60s 首增量阈值**硬编码常量**，不进 `config.properties`（不新增配置项、不改设置窗），仅留包级可见字段供单测覆写
- 用户主动中断优先于一切重试判定（现状已如此；实现保障见第 4 节"cancel() 路径"一条）

## 设计

### 1. 墙钟计时改造（RetryPolicy 零改动）

`RetryPolicy.isExhausted(long elapsedMs)` 本就是"传什么计时什么"，语义由调用方决定。`transientErrors()` 参数保持 `(5000, 0, 5000, 20*60*1000L)` 不变，仅改注释。

`AgentLoop`（469-502）与 `SubAgentLoop`（98-135）两处重试循环，删掉 `long waited` 累计，改为进入重试态时取基准：

```java
long retryStart = System.currentTimeMillis();   // 进入重试态时取一次
...
long delay = retryPolicy.delayMs(attempts);
if (!sleepWithInterruptCheck(delay)) break;
long elapsed = System.currentTimeMillis() - retryStart;
if (retryPolicy.isExhausted(elapsed)) {
    ui.onError(tag + " 重试了 " + attempts + " 次，持续 " + (elapsed / 60000) + " 分钟仍失败，已停止重试");
    ...
}
```

- 耗尽判定位次保持在"睡完 5s 之后、发起请求之前"，因此实际总时长超出上限最多一个尝试周期（≤65s），可接受
- 总结文案的"持续 X 分钟"改用真实 `elapsed`，不再用睡眠累计

### 2. isTransientError 扩展

`AgentLoop:635` 与 `SubAgentLoop:198` 各一份（保持两处字面一致，本次不抽公共组件）：

```java
private boolean isTransientError(LlmException e) {
    return e.type == LlmException.Type.RATE_LIMIT
            || e.type == LlmException.Type.TIMEOUT
            || (e.type == LlmException.Type.NETWORK && e.retryable)
            || e.httpCode == 500 || e.httpCode == 502;
}
```

- 网络类是否长重试由 `LlmException.retryable` 决定：客户端识别为永久性故障（DNS 解析失败）时抛 `retryable=false`，此处即不放行 → 走 else 分支一次性 `ui.onError` 报错，不进重试态、指示器不显示重试文案。复用既有字段，不给 `Type` 加枚举值

- 两处循环的进入判定（`AgentLoop:462` 的 `if (interrupted)`、`SubAgentLoop:93` 的 `Thread.currentThread().isInterrupted()`）都在 `isTransientError` **之前**，循环内 catch 也同样前置检查——这是把 NETWORK 纳入长重试的安全前提（见风险节）
- 原 `e.retryable && retries < 1` 快速重试分支保留，此后仅覆盖 503/504 等

### 3. 各错误类型在 20 分钟墙钟内的实际次数

| 错误类型 | 单次失败耗时 | 约重试次数 |
|---|---|---|
| 429 / 500 / 502 | 请求快速失败 + 5s | ~215 次（旧实现固定 239 次，略降） |
| TIMEOUT（首增量 60s 看门狗） | 60s + 5s | **~18–19 次** |
| NETWORK（拒连 / reset，秒级失败） | <1s + 5s | ~200 次 |
| NETWORK（connect 满 30s 超时，归类 TIMEOUT） | 30s + 5s | ~34 次 |
| NETWORK + DNS 解析失败 | 毫秒级 | **0 次，一次即报错**（短路，见第 4 节） |

### 4. 首增量看门狗（DeepSeekClient）

现状：`CONNECT_TIMEOUT=30s`、`READ_TIMEOUT=300s`。SSE 下 read 超时的含义是"两次字节之间的间隔上限"，故一次卡死最坏耗时 300s。

改法：`READ_TIMEOUT` **保持 300s 不动**（不误杀"模型持续在生成、但整体很慢"的流），另加"发出请求后 60s 内未收到任何有效增量即判定超时"。

- 新增字段 `long firstTokenTimeoutMs = 60_000L;`（包级可见，默认硬编码；单测可改小）
- 类内共享单线程 daemon `ScheduledExecutorService`（`private static final` 线程工厂设 daemon），`close()` 中 `shutdownNow()`
- `streamChat` 内：

```java
final boolean[] watchdogFired = new boolean[1];
ScheduledFuture<?> wd = watchdog.schedule(() -> {
    watchdogFired[0] = true;
    call.cancel();                       // 解除本线程 readUtf8Line() 阻塞
}, firstTokenTimeoutMs, TimeUnit.MILLISECONDS);
```

- **锚点是首个有效 delta**，不是 HTTP headers——SSE 的响应头在连接建立后立即到达，完全不代表模型开始生成。判定条件：首次出现非空 `content` / 非空 `reasoning_content` / 非空 `tool_calls` 增量时 `wd.cancel(false)`；`finally` 兜底再 cancel 一次
- `catch (IOException e)` 的归类顺序调整为：

```java
if (watchdogFired[0]) throw new LlmException(Type.TIMEOUT,
        "请求超时：" + (firstTokenTimeoutMs / 1000) + " 秒内未收到模型输出", true); // 必须在最前；
        // 阈值从字段动态取值，测试改小时文案不失真
if (isTimeout(e))     throw new LlmException(Type.TIMEOUT, "请求超时: " + e.getMessage(), true);
if (isPermanentNetwork(e)) throw new LlmException(Type.NETWORK,
        "网络错误: " + e.getMessage() + "（域名无法解析，请检查设置中的 API 地址）", false);
throw new LlmException(Type.NETWORK, "网络错误: " + e.getMessage(), true);
```

- 原因：okhttp 被 cancel 时抛的是 `IOException("canceled")`，不先判 `watchdogFired` 就会被错归为 NETWORK，且会被误当成用户中断的余波。
- `isPermanentNetwork(IOException e)`：沿 `getCause()` 链（限深 5 层，防自环）查找 `java.net.UnknownHostException`。okhttp 在选路失败时可能直抛也可能包成 `IOException("Failed to connect to ...")`，故必须查链而非只查 `e` 本身；**只查 DNS 这一种**，`ConnectException`/`SSLException` 不算
- `cancel()`（用户 Ctrl+C / 打断）路径下 `watchdogFired` 保持 false，异常仍归 NETWORK，但 `interrupted` 标志已置位 → 循环在判定 `isTransientError` 前就 break，不产生重试。零回归
- 非 2xx 响应在毫秒级抛出，与看门狗无关；`completeChat` 委托 `streamChat`，上下文压缩等调用点自动获得同样保护

### 5. RetryProgress 扩展（网络类错误无 HTTP 码）

当前 `RetryProgress` 只有 `(attempt, httpCode, body)`，网络类错误 `httpCode==0` 会被 `RunningIndicator.codeLabel(0)` 渲染成 `HTTP 0`。新增第四字段与两个工厂，把"异常 → 进度"的映射收在一处：

```java
public final String label;   // null=HTTP 错误（按 httpCode 出标签）；非 null=网络类中文标签

public static RetryProgress ofNetwork(int attempt, String label, String detail)  // httpCode=0，body=detail
public static RetryProgress from(int attempt, LlmException e)
    // TIMEOUT → ofNetwork(attempt, "网络超时", e.getMessage())
    // NETWORK → ofNetwork(attempt, "网络错误",  e.getMessage())
    // 其他    → of(attempt, e.httpCode, e.body)
public static String tag(LlmException e)   // 超时总结文案前缀："429"/"500"/"502"/"网络超时"/"网络错误"
```

- `of(attempt, httpCode, body)`、`none()` 签名保留，既有调用与断言零改动
- `from()` 只做**归类**，`detail` 原样传 `e.getMessage()`；前缀剥离与拼接是展示逻辑，留在 `RunningIndicator`（值对象不掺 UI 规则）
- 两个循环内的 `int lastCode` / `String lastBody` 简化为保存最近一次 `LlmException last`，指示器用 `RetryProgress.from(attempts, last)`，总结文案前缀用 `RetryProgress.tag(last)`（避免网络类错误输出 `0 重试了 N 次`）

### 6. RunningIndicator 文案

- `codeLabel(int)` 逻辑上移到 `retryText`：`p.label != null ? p.label : codeLabel(p.httpCode)`
- `bodyPart(p)`：`p.label != null`（网络类）→ 先剥掉 `detail` 自带的 `"网络错误: "` / `"请求超时: "` 前缀（该信息与 label 重复），再加 `：` 分隔；HTTP 类维持原样直拼 body（响应体是 json，直拼可读性已够），保持零回归。截断仍 200 字符
- 效果：`正在加载中...(网络超时，重试第3次：60 秒内未收到模型输出)`、`可随时补充信息...(网络错误，重试第7次：Failed to connect to api.xx.com/10.1.2.3:8000)`
- 基础文案冻结、首个流式增量复位、10s 轮换等机制全部不动

## 错误提示汇总

| 场景 | 指示器文案 |
|---|---|
| 429 重试中 | `正在加载中...(429限流，重试第N次{body})`（现状不变） |
| 500/502 重试中 | `正在加载中...(500服务报错，重试第N次{body})`（现状不变） |
| 网络超时重试中 | `正在加载中...(网络超时，重试第N次：{剥前缀后的原因})` |
| 网络错误重试中 | `正在加载中...(网络错误，重试第N次：{剥前缀后的原因})` |
| DNS 解析失败（不重试） | 正文红字一次：`网络错误: <原因>（域名无法解析，请检查设置中的 API 地址）` |
| 重试超时（主循环） | `{标签} 重试了 N 次，持续 X 分钟仍失败，已停止重试` |
| 重试超时（子 agent） | `子 agent {标签} 重试了 N 次，持续 X 分钟仍失败，已停止重试` |

## 已知取舍

1. **短路只覆盖 DNS 一类**：`connection refused`（端口写错、服务未起）与 TLS 配置错仍会重试满 20 分钟——内网服务重启期必然短暂拒连，放行重试的收益大于"填错端口多等 20 分钟"的代价。用户已确认此取舍
2. **DNS 短路的误判面**：本机 DNS 服务器临时抽风也抛 `UnknownHostException`，此时会被当成"地址配错"一次报错而非自动撑过去。发生率低且用户重发一次即可，换取配错地址时的秒级反馈
3. **429/500/502 次数从固定 239 次降到 ~215 次**：墙钟把每次失败请求的耗时也算进来了。这是语义修正的必然结果
4. 主/子循环的重试代码仍是两份重复实现，本次不抽公共组件（YAGNI；两处判定条件与文案需人工保持同步）

## 范围外（不做）

- SSE 中途断流（已吐字后失败）的续传与重试
- 503/504 等其他 5xx 长重试
- 首增量阈值配置化（`config.properties` / 设置窗）
- 重试逻辑重构为独立可测组件
- okhttp `callTimeout`（整请求硬上限）——与"流式可长时间生成"冲突，不使用
