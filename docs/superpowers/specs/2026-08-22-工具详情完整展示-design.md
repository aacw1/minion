# 工具详情完整展示 — 设计文档（2026-08-22）

## 背景与目标

聊天区工具调用信息展示不完整，影响审核与排查：

1. **工具调用（TOOL_CALL）参数被截断**：`ChatView` 渲染时 `shorten(data, 120)` 只显示前 120 字符——Edit/Write 的 oldString/newString 往往几百上千字符，**看不到改了什么**（审核场景核心诉求）。
2. **工具结果（TOOL_RESULT）成功时完全不显示输出**：`SessionController.onToolResult` 成功只传 `"ok"`，聊天区只渲染 `✅ 名称 成功`——Bash 命令输出、Edit 结果全文不可见。
3. **失败原因只取首行**：`toolFailureDetail` 截断 120 字符，多行错误只能看到第一行。
4. **会话恢复重演后结果丢失**：`replayHistory` 对 TOOL_RESULT 统一按 `"ok"` 重演，历史里存的完整 output 未使用。

目标：工具调用与结果**完整展示**（打印多不要紧），并提供折叠能力控制长内容占用。

已确认的需求边界（用户澄清）：
- **范围**：只改聊天区（【工具】/【系统】段渲染）；高危确认卡片（ConfirmSheet）保持现状
- **折叠形式**：所有工具详情内容可手动折叠/展开；内容 ≥500 字符时**默认折叠**，短内容默认展开但可手动收起
- **Bash 输出上限**：保持工具层 3 万字符截断（LLM 防爆上下文设计），GUI 显示截断后的完整内容，不改工具层
- **Edit/Write 展示**：生成行级 diff（`-` 旧行 / `+` 新行），比原文两段更直观

## 现状分析

| 位置 | 现状 | 问题 |
|---|---|---|
| `SessionController.onToolResult` | 成功传 `"ok"`，失败传 `"error:"+output` | 成功丢弃 output |
| `ChatView` TOOL_CALL 分支 | `shorten(args, 120)` | 长参数（Edit/Write 新旧文）看不到 |
| `ChatView` TOOL_RESULT 分支 | 成功 `✅ 名称 成功`；失败首行截断 120 | 输出不显示、原因不完整 |
| `ChatView.toolFailureDetail` | 取原因首行 + shorten 120 | 多行错误丢失 |
| `SessionController.replayHistory` | TOOL_RESULT 硬编码 `"ok"` | 恢复会话后结果不可见 |
| `Message.toolResult` 历史存储 | content 存完整 output | 数据其实在，只是没展示（重演可用） |

## 方案对比

| 方案 | 思路 | 权衡 |
|---|---|---|
| **A（采用）** | 字符串编码扩展：`onToolResult` 成功传 `"ok\n"+output`；ChatView 内做完整渲染 + 折叠 + diff（新增 `SimpleDiff`、`CollapsibleText` 两个纯逻辑/自包含组件） | EventList 结构零改动、改动集中、可单测；`data.startsWith("ok")` 现有判断保持兼容 |
| B | `EventList.Ev.data` 结构化（携带 ToolResult 对象、工具调用信息） | 类型清晰但 EventList/重演/测试全要动，收益不大（YAGNI），否决 |
| C | 只去截断不折叠不做 diff | 不满足用户已确认的折叠与 diff 需求，否决 |

## 详细设计（方案 A）

### 1. SessionController.onToolResult：成功携带完整输出

```java
@Override public void onToolResult(String name, ToolResult result) {
    if (result == null) {
        events.add(new EventList.Ev(EventList.Kind.TOOL_RESULT, name, "ok"));
    } else if (result.ok) {
        // "ok" 前缀保持 ChatView 现有 ok 判断兼容；换行后接完整输出
        events.add(new EventList.Ev(EventList.Kind.TOOL_RESULT, name, "ok\n" + result.output));
    } else {
        events.add(new EventList.Ev(EventList.Kind.TOOL_RESULT, name, "error:" + result.output));
    }
}
```

兼容性：`ChatView` 现有 `data.startsWith("ok")` 判断对成功态不变；失败态 `"error:"` 前缀不变。

### 2. SessionController.replayHistory：重演完整输出

TOOL_RESULT 分支：用 `m.content`（历史存的完整 output）替代硬编码 `"ok"`：

```java
events.add(new EventList.Ev(EventList.Kind.TOOL_RESULT, m.name,
        m.content == null || m.content.trim().isEmpty() ? "ok" : "ok\n" + m.content));
```

AskUserQuestion 回答重演逻辑（先 USER_SUPPLEMENT 再 ✅ 行）保持不变。历史 TOOL 消息无成败标记，统一按成功态重演（与现语义一致）。

### 3. ChatView TOOL_CALL 渲染：完整参数 + Edit/Write diff

- **Bash**：完整命令（通常 <500 字符平铺；≥500 同样走默认折叠规则）
- **Edit/Write**：解析 args 的 `path`/`oldString`/`newString`，用 `SimpleDiff` 生成行级 diff 展示；标题行含路径
- **其他工具**：完整参数 JSON
- **AskUserQuestion**：保持现有 `❓ 模型向你提问` 格式（其参数即问题文本，平铺）

diff 展示体例：

```
⛭ Edit → src/foo.java
- 旧行1
- 旧行2
+ 新行1
（上下文公共行不显示，仅显示变更行，变更行数少时直接平铺）
```

### 4. ChatView TOOL_RESULT 渲染：完整输出 + 折叠

- 成功：`✅ 名称 成功` 摘要行 + 输出全文（`"ok\n"` 前缀后的内容；空输出只留 ✅ 行）
- 失败：`❌ 名称 失败` 摘要行 + 完整原因（`"error:"` 前缀后的内容，不再首行截断）
- 内容 ≥500 字符 → 默认折叠；<500 → 默认展开；均可手动切换
- `toolFailureDetail` 删除（原因完整展示后不再需要首行摘要拼接）——同步删除其单测，替换为编码格式单测

### 5. 新增 SimpleDiff（行级 diff，纯逻辑可单测）

- 位置：`com.minion.gui.chat.SimpleDiff`（无 JavaFX 依赖）
- 算法：LCS 动态规划（O(n×m)，工具参数几百行内足够；不引入 Myers，YAGNI）
- 输出：行列表，每行 `(前缀, 内容)`，前缀 ∈ `-`（仅旧）/ `+`（仅新）/ ` `（公共行，可过滤）
- 行尾归一化：输入按 `\r?\n` 切行，CRLF 兼容（与 EditTool 归一化思路一致）
- 空 oldString → 全部为 `+` 行；空 newString → 全部为 `-` 行

### 6. 新增 CollapsibleText（折叠展示组件）

- 位置：`com.minion.gui.chat.CollapsibleText`（JavaFX 节点）
- 结构：标题行（摘要 + `▸ 展开（N 字符）` / `▾ 收起`，点击切换）+ 内容体（复用 `MessageTextArea` 高度自适应）
- 默认状态：内容 ≥500 字符（常量 `COLLAPSE_THRESHOLD`，可调）→ 默认折叠；否则默认展开
- 折叠/展开状态手动可逆：折叠态点击展开、展开态点击收起
- 与 ChatView 现有 Seg 结构协作：CollapsibleText 作为一段的 body 节点（`append` 的 text 参数不变，body 由 ChatView 在需要时包成 CollapsibleText）

### 7. 边界情况

- 空 output：不渲染正文，只留 ✅/❌ 摘要行
- diff 变更行很多（≥500 字符）：同样走默认折叠
- AskUserQuestion 回答重演：`m.content` 即回答文本，走 USER_SUPPLEMENT，不误入 TOOL_RESULT 输出展示（先判断 `"AskUserQuestion".equals(m.name)`，现有逻辑保持）
- 事件缓冲/切会话重放：Ev 结构未变，`data` 仍是 String，无序列化兼容问题
