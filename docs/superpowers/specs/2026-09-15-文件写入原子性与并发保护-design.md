**探针 5 — 精确闭环：事故那个 `0x89` 是哪个字符的哪一字节**

```
「）」U+FF09 的 UTF-8 编码 = EF BC 89          ← 中文设计文档里最常见的标点之一
长方内容 size L = 7338   短方内容 size S = 75
切割点 S 落在长方 EF BC | 89 之间

交错后最终文件:
  size = 7338（= L，短方写入未截断长方尾部）
  残留首字节 fin[S] = 0x89                     ← 事故现场报告的损坏字节
  残留区 hex: 89 0A E5 90 8E E7 BB AD ...      ← 0x89 后紧跟 0x0A，即「末尾多出一行损坏字节」
  合法 UTF-8? false    合法 GBK? false         ← Read 报「疑似二进制」

反证（单线程顺序写）:
  size = 75（= S，旧尾部已被 TRUNCATE_EXISTING 截断）  合法 UTF-8? true
  → 损坏【不可能】由单线程覆盖写产生

其他含 0x89 的常见汉字：「厉」= E5 8E 89
```

> 两类后果的**发生门槛不同**，需分别理解：
> - **丢更新**：只要两次 read 都发生在任一 write 之前即成立 —— 门槛极低，**2 个并发 Edit 就 29/30 轮复现**（探针6），4 个并发时 240 处改动仅生效 61 处（探针4）。
> - **损坏字节**：还需额外命中窄时序窗口 —— 短写方的 `open(TRUNCATE)` 必须早于长写方的 `write`、而短写方的 `write` 又晚于长写方的 `write` 完成（此时文件长度已被长写方撑到 L，短写方只覆盖 `[0,S)`，`[S,L)` 成为残留尾部）。2 线程 30 轮命中 0 次，4 线程 60 轮命中 19 次（32%，探针4），2 线程 300 轮命中 76 次（探针2）。**低概率但真实发生 = 本次事故**。

### 1.4 三个提问的明确回答

**Q1：`0x89` 的确切成因 —— 交错写，还是 truncate 未生效残留旧尾部？**

> **是两个 `Files.write` 交错写同一 inode**，不是 truncate 失效。
>
> - 单线程覆盖写实测 `size=36000 → 3`、内容 `"END"`，`TRUNCATE_EXISTING` 完全生效（探针1 + 探针5 反证），**排除**"覆盖写变短后残留旧尾部"。
> - 真实成因：两个 channel 各自 `open` 时各自 truncate、各自维护 **独立 position**。长写方先完成把长度撑到 `L`；短写方后完成只覆盖 `[0, S)`，**不会**把长度收回 `S` → `[S, L)` 保留长写方的残留尾部（探针2 逐字节验证 `尾部残留 == 长写方[min..len)` 为 `true`）。
> - `0x89` 的来源：切割点 `S` 落在长写方某个 UTF-8 三字节字符内部。探针5 精确复现——全角右括号 `）`(U+FF09) = `EF BC 89`，当 `S` 落在 `EF BC | 89` 之间，残留首字节正是 **`0x89`，且其后紧跟 `0x0A`**，与事故描述「文件末尾多出一行损坏字节（含 0x89）」一字不差。`0x89` 亦见于「厉」= `E5 8E 89`。
> - 为什么 GBK 也不合法：`0x89` 作 GBK 首字节需后跟 `0x40-0xFE`，实际后跟 `0x0A` → 解码失败 → `Read` 报「疑似二进制」。
> - 探针2 的孤立字节直方图覆盖 `0x80/0x82/0x87/0x8A/0x8C/0x8E/0x8F/0x90/0x9C/0xA0/…/0xBE`，即整个续接字节区间 `0x80-0xBF`；`0x89` 属同一分布，只是取决于切割点落在哪个字符内部。

**Q2：除 AgentLoop 并行 tool_call 外，还有哪些并发写路径？**

| 编号 | 路径 | 是否风险 | 说明 |
|---|---|---|---|
| a | 主 agent 同轮并行 `tool_call`（`AgentLoop:663-665`，池宽 4） | ★ **事故路径** | 两个 Write/Edit 改同一文件 |
| b | 同轮多个 `task` 子代理并行（子代理内部串行，但子代理之间、子代理与主 agent 其他工具之间并行，共用同一 4 线程池） | ★ 同类风险 | `TaskTool` 无独立池，经 `AgentLoop.runSubAgent` 在同一池内执行 |
| c | 同一轮 `Write`/`Edit` 与 `Bash` 重定向（`> file`、`sed -i`）写同一文件 | ★ 存在 | `BashTool` 走子进程，**进程内锁无法覆盖**（只能靠原子写保证不产坏文件） |
| d | 写与读交错：`Edit` 回写期间 `Read`/`Grep` 读同一文件 | 中 | 实测直接写有 1/200 撕裂读（探针3-G）→ 模型读到半截文件被误导；原子写后为 0 |

**Q3：跨进程场景是否存在？进程内锁是否足够？要不要 FileLock？**

> - **场景存在**：`Main` / `Boot` / `SessionManager` 均无单实例保护（grep 确认无 `ServerSocket` / `FileLock` / 单实例逻辑），用户可对同一工作区启动两个 minion 实例。
> - **进程内锁不足以覆盖跨进程**，但 **FileLock 与原子写在 Windows 上直接冲突**：
>   - 锁**目标文件**：探针3-E 实测目标被持有读句柄时 `ATOMIC_MOVE` 抛 `AccessDeniedException`；持有写锁时 rename 替换同样失败 → 与原子写互斥，不可行。
>   - 锁 **tmp 文件**：锁的是 tmp 的 inode，`move` 之后锁随 tmp 消失，**锁不住 rename 语义** → 无效。
>   - 唯一可行形态是**旁路锁文件**（如 `jarDir/.session/locks/<hash(path)>.lock` 上 `tryLock`），代价：新增锁目录与生命周期管理、每次写多一次 open/lock/close、崩溃残留锁文件（`FileLock` 随进程退出自动释放，残留文件本身无害）。
> - **本次取舍**：采用「**原子写 + 进程内路径锁**」。跨进程场景下**保证不产生损坏文件**（原子写已实测做到），但**不保证跨进程丢更新**。理由：同进程同轮并行已实测 60/60 轮丢更新、32% 轮产坏文件，是现实高发路径；跨进程双实例编辑同一文件属低频，且用旁路 FileLock 换来的收益小、复杂度与 Windows 语义坑多。跨进程互斥列为 **P3 备选**（见 §6），更经济的根治手段是后续加"单实例检测"。

| 方案 | 实测/分析结论 | 采纳 |
|---|---|---|
| **A. 统一原子写工具类**（`*.tmp` + `ATOMIC_MOVE`，复用既有模式） | 探针3-D：300 轮并发原子写 → **混杂 0、非法 UTF-8 0**；探针3-G：读侧撕裂 **0/200**。**能彻底消除缺陷①**（含 `Bash` 重定向等进程内锁管不到的路径 c，只要对方也走原子写；对子进程写入仍无能为力）。**不能消除缺陷②**（171/126 分布说明仍是"后者胜"） | ✅ **必做** |
| **B. 进程内路径串行锁**（覆盖 Edit 的读-改-写全周期） | 探针3-F：无锁 **1/8** 生效 → 有锁+原子写 **8/8** 生效。**能彻底消除缺陷②**（同进程内，含路径 a/b） | ✅ **必做** |
| **C. AgentLoop 层按路径分组串行** | 与 B 职责重叠（重复防线）；需在主循环预解析每个 `tool_call` 的 `args.path`，且解析口径必须与 `PathsGuard`（相对路径/符号链接/`toRealPath`）完全一致，否则分组失效或误分组 —— 复杂度与出错面大；且**无法覆盖跨轮并发**（子代理与主 agent 并行）；还会降低无关工具的并行度 | ❌ 不做 |
| **D. 写后回读校验** | 原子写后文件必然完整（探针3-D/G 已证），全量回读解码的边际价值低、IO 翻倍。**采纳轻量版**：只校验 `Files.size(target) == 预期字节数`，不符则报错并返回失败 `ToolResult`（防 move 降级路径下的意外截断），**不做**回读解码 | ⚠️ 轻量采纳 |
| **E. 拒绝并发写、返回失败让模型重试** | B 的锁已把并发写串行化（等待时间 = 对方一次写盘，毫秒级），无需拒绝；拒绝会白白多一轮 LLM 往返与 token 消耗。仅保留**锁等待超时**兜底（见 §4.3） | ❌ 不做（保留超时兜底） |

**结论：A + B 对同进程场景已充分**（A 治损坏、B 治丢更新，实测各自 0 残留 / 8-8 全生效），D 作为低成本纵深防御，C/E 性价比低不采纳。

## 4. 采纳方案与改动边界（最小面积）

### 4.1 新增 2 个类（`core/tools/` 内，无新依赖，JDK8）

**`core/tools/AtomicFiles.java`** — 原子写工具类（统一项目既有 tmp+move 模式）

```java
public final class AtomicFiles {
    /** 原子写文本：唯一 tmp + ATOMIC_MOVE，失败降级 REPLACE_EXISTING，末尾校验长度 */
    public static void writeText(Path target, String content, Charset cs) throws IOException;
    /** 原子写字节（同上，供非文本调用方复用） */
    public static void writeBytes(Path target, byte[] data) throws IOException;
}
```

实现要点（每条都有实测依据）：
1. `Files.createDirectories(target.getParent())`（保留 `WriteTool:64` 既有行为）
2. tmp 名 **唯一**：`<name>.mt<nanoTime>-<threadId>.tmp`，与 target **同目录**（跨目录 move 不保证原子）；同时修掉缺陷⑥的 tmp 互踩隐患
3. `Files.write(tmp, data)` → `Files.move(tmp, target, REPLACE_EXISTING, ATOMIC_MOVE)`
4. **`ATOMIC_MOVE` 失败必须降级** `Files.move(tmp, target, REPLACE_EXISTING)`：探针3-E 实测 Windows 上目标被读句柄占用（编辑器/IDE/杀软/并发 `Read`）时 `ATOMIC_MOVE` 抛 `AccessDeniedException`，降级则成功。降级后仍是一次 move（写入完整、长度正确），仅失去"读侧零撕裂"保证 —— 可接受
5. `finally` / `catch` 中 `Files.deleteIfExists(tmp)`，失败不留垃圾（对齐 `ModelManager:155-157` 既有约定）
6. 写后校验（方案 D 轻量版）：`Files.size(target) != data.length` → 抛 `IOException("写入校验失败…")`，**绝不静默产出坏文件**
7. tmp 后缀名过长导致 Windows `MAX_PATH` 超限时，捕获 `IOException` 后**降级为直接 `Files.write(target, data)`** 并在异常消息中标注（避免长路径文件从"能用"变成"不能用"的回归）

**`core/tools/PathLocks.java`** — 进程内按规范化路径的串行锁（striped）

```java
public final class PathLocks {
    /** 取该路径对应的锁（striped：固定 256 条，避免 map 无限增长泄漏） */
    public static ReentrantLock forPath(Path p);
}
```

实现要点：
1. key = `p.toAbsolutePath().normalize()`（与 `PathsGuard` 口径一致；**不用** `toRealPath()`——目标可能尚不存在，且 `toRealPath` 抛 IOException）
2. **固定 256 条 `ReentrantLock` 按 hash 取模**（striped），而非 `ConcurrentHashMap<Path,Lock>` 无限增长 —— 长期运行的常驻进程不应因写过的路径数累积锁对象；代价是极少数不同路径伪冲突（多串行一次毫秒级写盘），可接受
3. `ReentrantLock` 可重入 → 同线程嵌套调用（如 `Write` 内部再触发写）不死锁

### 4.2 改 2 处工具（每处 3-6 行）

**`WriteTool.execute`（`:64-67`）**
```java
if (p.getParent() != null) Files.createDirectories(p.getParent());
String content = args.get("content").getAsString();
byte[] data = content.getBytes(StandardCharsets.UTF_8);
ReentrantLock lock = PathLocks.forPath(p);
if (!lock.tryLock(LOCK_WAIT_SECONDS, TimeUnit.SECONDS))
    return ToolResult.error("文件正被其他操作占用，稍后重试: " + p);
try {
    AtomicFiles.writeBytes(p, data);
} finally { lock.unlock(); }
return ToolResult.success("已写入 " + p + " (" + content.length() + " 字符)");
```

**`EditTool.execute`（`:67` 与 `:91`）** — 锁必须覆盖 **read → modify → write 全周期**
```java
ReentrantLock lock = PathLocks.forPath(p);
if (!lock.tryLock(LOCK_WAIT_SECONDS, TimeUnit.SECONDS))
    return ToolResult.error("文件正被其他操作占用，稍后重试: " + p);
try {
    TextFiles.Decoded d;
    try {
        d = TextFiles.decode(Files.readAllBytes(p));
    } catch (RuntimeException e) {                    // 缺陷③

                + "请先用 Read/Bash 确认文件状态: " + p);
    }
    … 原有 CRLF 归一化 / 匹配 / 替换逻辑完全不变 …
    AtomicFiles.writeBytes(p, updated.getBytes(d.charset));   // 按原编码写回（保留既有契约）
} finally { lock.unlock(); }
```

### 4.3 三个关键设计细节（易踩坑，务必按此实现）

1. **锁必须在"确认之后"获取**：`EditTool:58-61` / `WriteTool:60-63` 的越界确认（`confirm.checkEscapeWrite`）会**阻塞等待用户点击**。若把锁加在 `execute` 开头，用户不点确认就持锁挂死，其他写同一文件的工具全部阻塞 → **锁的获取点必须在所有 `confirm` 调用之后、`Files.readAllBytes` 之前**（上面代码已按此放置）。
   （`AgentLoop:811` 的高危确认在 `execute` 之外，天然不受影响。）
2. **`tryLock` 带超时而非无限 `lock()`**：常量 `LOCK_WAIT_SECONDS = 30`。防止未来有人在锁内引入阻塞调用（如新的确认弹窗）造成工具线程永久挂死；超时返回明确失败 `ToolResult`，模型可自行重试（这是方案 E 的"兜底"而非"主策略"）。
   注意 `tryLock(timeout)` 抛 `InterruptedException` → 恢复中断标志并返回失败 `ToolResult`（对齐 `AgentLoop` 的取消语义）。
3. **不改变任何既有对外契约**：`WriteTool` 的 UTF-8 写、`EditTool` 的**按原编码写回**（`d.charset`）、CRLF 归一化匹配、越界守卫顺序（T8 约定：存在性/目录检查在守卫之前）、`ToolResult` 文案主体，全部保持原样。

### 4.4 缺陷④ 撤回（实施期实测推翻原判断）

原判断：`GrepTool:152` 只 `catch (IOException)` 会被 `TextFiles.decode` 的 unchecked 异常穿透中断。

**实测不成立**：GrepTool 走的是 `TextFiles.readAllLines`（`GrepTool:130`），该方法在 `Files.readAllLines` 上做 UTF-8→GBK 降级，两码都失败时抛的是 `MalformedInputException`（`IOException` 子类），被既有 `catch (IOException ignored)` 正常捕获 → 单个损坏文件被跳过，搜索照常完成。对应测试 `grep_corruptFile_doesNotAbort` 在**未改一行代码**的情况下直接通过，故不做该改动（避免无依据的改动，符合"最小面积"）。

### 4.5 明确不做（控制面积）

- 不动 `AgentLoop` 调度（方案 C）
- 不动 `TextFiles.decode` 的语义与其 3 个调用方的整体行为（只在 `EditTool`/`GrepTool` 捕获 unchecked）
- 不动 `OutputDump` / `TruncatedOutput` / `BashTool` 临时脚本 / `ShellLocale` 探针文件（唯一文件名或临时探针，无并发冲突）
- 不引入 `FileLock` / 跨进程锁 / 单实例检测（§7 决策项 1）
- 不做 tmp 孤儿文件的启动清理（写入窗口毫秒级、`finally` 已清理，收益不抵复杂度）
- 不顺手重构 `SessionStore`/`ModelManager`/`WorkspaceManager`/`McpStore`/`ToolStore`（§7 决策项 3 待用户定）
