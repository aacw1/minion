# 压缩保留区保底四组设计

日期：2026-09-14
状态：已确认（2026-09-14；用户选定：常态保底 4 组 / 危险区（≥85%）降为 1 组 / 手动 `/compact` 同规则）
来源：承接《压缩保留区 token 预算化》（v2）——保留区已按 token 预算自适应，但保底仅最新 1 组：最新一组偏大时会单独占满预算、把第 2、3 组一并压掉

> 术语说明：用户表述的「原子对」即代码中的**原子组**（`chunkGroups` 的分组单位：普通 user / 无工具调用的 assistant 各自一组；`assistant(tool_calls)` 与其 tool 结果捆为一组）。

## 1. 背景与问题

### 1.1 现状（v2 已落地）

`ContextManager` 保留区算法：从最新组往前累加 token，累计 ≤ 预算（`0.13×max`，200k → 26k）的**最大**组数，**保底最新 1 组**（`KEEP_MIN_GROUPS = 1`，哪怕自身超预算）。

- 200k 窗口、组均 6-7k token 时，预算内约留 3-4 组——「约 4 组」多数时候成立，但**不保证**；
- 最新一组若为大输出（如 25k token），它单独占满预算 → 第 2、3 组全部被压入摘要 → 最近对话细节丢失（正在进行的任务链被摘要化）。

### 1.2 目标

1. 常态下**最近 4 个原子组绝不被压缩**（保真：正在进行的任务链、刚读到的文件与决策）；
2. 贴窗保命场景（`estimate ≥ 85%×max`）保底**降为 1 组**，保证压缩仍能腾出空间——不引入「压不动」回归；
3. 手动 `/compact` 与自动同规则（含危险区降级）。

### 1.3 非目标

- 不改保留区预算（`KEEP_BUDGET_RATIO = 0.2`）、收益门槛（`MIN_COMPRESSIBLE_RATIO = 0.05`）、危险区阈值（`FORCE_COMPRESS_RATIO = 0.85`）、摘要上限（5000 字）；
- 不改 `chunkGroups` 分组规则、不改压缩指令、不动配置项（`config.properties`）与 GUI；
- 不做「保底组数按窗口自适应」：小窗口下 4 组占比天然更大，自动落到危险区降级路径、行为退化为现状（见 §2.4），无需专门逻辑。

## 2. 设计

### 2.1 常量（`ContextManager`）

| 常量 | 值 | 说明 |
|---|---|---|
| `KEEP_MIN_GROUPS` | `1` → **`4`** | **常态保底**：最近 4 组无条件保留（哪怕合计超预算） |
| `KEEP_CRITICAL_GROUPS`（新） | `1` | **危险区保底**：`estimate ≥ 85%×max` 时降为最新 1 组（保命压缩优先，绝对保真让路） |
| `KEEP_BUDGET_RATIO` / `MIN_COMPRESSIBLE_RATIO` / `FORCE_COMPRESS_RATIO` / `THRESHOLD` / `SUMMARY_MAX_CHARS` | 不变 | 沿用 v2 |

### 2.2 算法

保底组数由当前占用决定，`compress` 与 `compressibleTokens` 共用同一判定（口径一致）：

```java
/** 本次压缩的保底保留组数：危险区降为 1 组（保命），常态保底 4 组（保真） */
private int minKeepGroups(List<Message> messages) {
    return estimate(messages) >= maxContextTokens * FORCE_COMPRESS_RATIO
            ? KEEP_CRITICAL_GROUPS : KEEP_MIN_GROUPS;
}
```

`keepCount` 循环内的 break 条件由 `keep >= KEEP_MIN_GROUPS` 改为 `keep >= minKeep`；返回值改为 **`return keep`**（循环语义已保证下限：不 break 直到 `keep ≥ minKeep` 或组耗尽；同时保证返回值 ≤ 组数，`take` 不会为负）：

```java
/** 保留的原子组数：从最新组往前累加 token，累计 ≤ 预算的最大组数；
 *  下限 minKeep（常态 4 组保底 / 危险区 1 组）；无上限（预算内尽量多留） */
private int keepCount(List<List<Message>> groups, int minKeep) {
    if (groups.isEmpty()) return 0;
    long budget = (long) (maxContextTokens * THRESHOLD * KEEP_BUDGET_RATIO);
    long acc = 0;
    int keep = 0;
    for (int i = groups.size() - 1; i >= 0; i--) {
        long t = TokenCounter.estimateMessages(groups.get(i));
        if (keep >= minKeep && acc + t > budget) break;
        acc += t;
        keep++;
    }
    return keep; // 组数 < minKeep 时返回组数本身（take=0 → 不压缩）
}
```

`compress(messages)` / `compressibleTokens(messages)` 均改为：

```java
int keep = keepCount(groups, minKeepGroups(messages));
int take = groups.size() - keep;   // 恒 ≥ 0
```

其余流程（`take <= 0` 同一引用返回、摘要置前、pinned/system 原样、旧摘要合并）**全部不变**。

### 2.3 行为变化（max = 200000：阈值 130k / 预算 26k / 门槛 10k / 危险区 170k）

| 场景 | v2 行为 | 本次行为 |
|---|---|---|
| 最近 4 组合计 60k（> 预算 26k，< 阈值 130k） | 只保最新 1-2 组（预算装满即停） | **保 4 组**（超预算仍保）；更早的组进入压缩批次 |
| 最近 4 组合计 140k（> 阈值 130k，< 危险区 170k） | 压不掉，提示「仍占/暂缓」 | 压不掉，提示「暂缓」（4 组保底占位）→ estimate 涨到 170k 后**降为 1 组 → 压得动** |
| 组数 ≤ 4 且超阈值 | 可能压缩（保底 1 组） | `take = 0` → **不压缩、不调 LLM**；涨到 85% 后降级压（保底 1 组，组数 ≥2 时 take ≥1） |
| 小组很多（预算能容全部） | `take = 0` | 不变（4 组只是**下限**，不是上限：预算内仍尽量多留） |
| 危险区（≥85%） | 保底 1 组（无条件压） | 不变（降级后同 v2） |

### 2.4 边界分析

- **65%~85% 区间**：4 组保底可能使可压量 < 门槛 → 「暂缓」（不调 LLM），任务推进后可压量增长即自动重试——沿用 v2 响应式门槛机制，如实提示、不设禁止标志；
- **≥85%**：降为 1 组；只要组数 ≥ 2 即 `take ≥ 1`，压缩必被发起（`worthCompressing` 危险区无条件 true），压后通常回到阈值下，保底随后恢复 4 组；
- **极端：组数 = 1 且超阈值**：危险区 `take = 0` → `compress` 同引用返回（NOTHING 静默）——v2 既有行为（终审已 park「危险区 + NOTHING 静默」），本次不变；
- **小窗口（如 64k）**：4 组占比天然更大，更多走危险区降级路径 → 行为自然退化为 v2，无回归。

### 2.5 兼容与影响

- **`AgentLoop` / `SubAgentLoop` 零改动**：保底逻辑全部收敛在 `ContextManager`；调用点（`shouldCompress` → `worthCompressing` → `compress`）语义不变。提示文案沿用：
  - 「自动压缩暂缓：可压内容不足（最近内容与常驻提示词已占 X%）……」（保底 4 组即"最近内容"的一部分，文案无失实）
  - 「自动压缩后上下文仍占 X%（大输出占满保留区）……」
- **事前门槛与实际压缩口径一致**：`compressibleTokens` 与 `compress` 共用同一 `minKeepGroups` → 不会出现「门槛通过但 take = 0」；
- **手动 `/compact`**：走同一 `compress` → 自动同规则（含危险区降级）；
- 旧会话无迁移问题（压缩是运行时行为，历史消息格式不变）；GUI/设置窗无变化。

## 3. 测试计划

### 3.1 `ContextManagerTest`

### 3.2 `AgentLoopCompactTest`

1. **常态保底 4 组**：4 组大 + 更早小组 → 压缩后最近 4 组完整保留（增强既有保留区断言的用例）；

## 4. 风险与取舍

| 风险 | 说明 | 缓解 |
|---|---|---|
| 压缩频率上升 | 常态保留区更大（可能超预算）→ 压后 estimate 更高 → 更早再次触顶，压缩次数与总 token 成本略升 | 保真是用户明确诉求（已知代价）；收益门槛（5%）避免零收益空转；摘要 ≤5000 字 |
| 4 组自身 > 阈值时有「空窗期」 | 65%~85% 区间压不动，只能提示 | 如实提示「暂缓」+ 危险区（85%）降级自动接管；超窗仍有服务端报错兜底（同 v2） |
| 小窗口下 4 组占比过大 | 更多落在降级路径 | 行为自然退化为 v2 现状，无回归；不做自适应（YAGNI） |
| 极端：组数 ≤1 超阈值 | `take = 0` → 静默 | v2 既有行为（终审已 park），本次不变 |

## 5. 验收标准

1. 常态：最近 4 组**不进入**压缩批次，即使其合计超出保留区预算；
2. 常态：4 组保底导致可压不足 → 不调 LLM + 「暂缓」提示一次；任务推进后自动重试；
3. 危险区（≥85%）：保底降 1 组 → 压缩必被发起（组数 ≥2）；压缩后回到阈值下、保底恢复 4 组；
4. 手动 `/compact` 同规则；
5. `mvn test` 全绿，无回归。

2. **常态用例窗口校准**：计划原稿 max=100 下 216 token ≥ 危险区 85，「常态（未进危险区）」前提不成立（会走降级路径）→ 改用 **max=260**（阈值 169 / 保留预算 33 / 危险区 221），场景语义不变。
3. **保留区预算按 long 截断**：`keepCount` 内 `(long)(max×0.65×0.2)`——max=260 → 33（33.8 截断）、max=70 → 9（9.1 截断），注释按截断值写（`0396e5a`）。
