# 低端机（远程桌面 / 无显卡 / 高分辨率）渲染与启动优化设计

日期：2026-10-31
状态：已实施（待验收）
前置：`2026-10-18-GUI低端机性能优化-design.md`、`2026-10-30-optimization-p0-6-p1-3-4-5-6-8-design.md`

## 一、现象与环境

用户反馈（非开发机）：

- 运行环境为**远程桌面、无独立显卡**；JavaFX 走 `prism.order=sw` 软件光栅化。
- **软件一打开就卡**，但此时只是显示一个空工作台（标题栏 / 侧栏 / 输入框 / 空消息区）。
- **屏幕分辨率越高越卡**，同一操作在低分辨率下明显更顺。

两条现象都指向"每帧要填的像素数"和"启动前串行工作"，而不是业务逻辑。

## 二、本机实测（JDK 8u181 + `-Dprism.order=sw`）

探针位于 `target/perf-probe`（不入库），全部为真实 JavaFX 场景、`AnimationTimer` 帧间隔统计。

### 2.1 启动（窗口可见时间，外部轮询 MainWindowTitle）

| 场景 | 耗时 |
| --- | --- |
| 最小 JavaFX 窗口（一个 Label） | **1.05 s** |
| 真实应用（`run/minion-0.1.0.jar`，3 个会话） | **2.6 ~ 3.8 s** |
| 其中 JavaFX 启动前串行装配 | 1.1 s（`SessionManager` 构造 1.1 s） |
| 其中 `SessionStore.list()+load()` 纯 JSON | 约 40 ms（冷启动 160 ms） |

采样剖析发现 `SessionManager` 构造的 1.1 s 里约 0.6~0.8 s 不在本项目代码：

```
okhttp3.OkHttpClient.<init>
  → SSLContext.init → SecureRandom.SeederHolder.<clinit>
    → SeedGenerator.addNetworkAdapterInfo → NetworkInterface.getAll   (Windows 枚举网卡，约 200ms)
    → javax.crypto.JceSecurity.<clinit> → JarVerifier 策略校验         (约 200ms)
```

即"启动时为每个历史会话 new 一个 OkHttpClient"把 JDK 的 SSL/JCE 一次性初始化
（网卡枚举 + 策略文件校验）拖到了窗口出现之前。

### 2.2 渲染（窗口 1280×760，`glass.win.renderScale=2` 模拟 150%+ 缩放的高分屏）

| 场景 | 软件渲染 1x | 软件渲染 2x |
| --- | --- | --- |
| 输入框聚焦发光（每 60ms 打一个字，4s） | 249 帧 / avg 15ms | **97 帧 / avg 39ms / max 80ms** |
| 同上，去掉发光 | 249 帧 / avg 15ms | **249 帧 / avg 15ms** |
| 消息区滚动（缓存关，当前实现） | 179 帧 / avg 16ms | **75 帧 / avg 39ms / p95 143ms** |
| 消息区滚动（缓存开） | 244 帧 / avg 15ms | **229 帧 / avg 16ms** |
| 流式输出（缓存关） | 176 帧 / avg 16ms | **69 帧 / avg 42ms / p95 143ms** |
| 流式输出（缓存开） | 239 帧 / avg 16ms | **145 帧 / avg 26ms** |
| 仅一个齿轮/状态点动画 | 187 帧 / 60fps | **136 帧 / avg 21ms** |

关键结论：

1. **高斯 `dropshadow` 是输入路径的头号热点**：它挂在输入大框上，而大框是输入框的父节点；
   每次按键的文本脏区都会让父节点整块重新做高斯模糊。2x 下从 60fps 掉到约 25fps。
   去掉后 2x 也满帧。
2. **`ScrollPane` 视口缓存**在高分屏/软件管线下收益极大：滚动 3 倍帧数、流式 2 倍帧数。
   当前实现对**所有**管线强制 `viewport.setCache(false)`（为修 es2 大纹理上传卡死），
   但软件管线没有 GPU 纹理上传问题，关缓存只剩"每次全视口重绘"的代价。
3. **JavaFX 8 的 HiDPI 渲染倍率按整数向上取**：Windows 150% 缩放 → `renderScale=2`，
   1280×760 的窗口实际光栅化 2560×1520（约 3.9 MP，是 1x 的 4 倍）。
   软件渲染下这就是"分辨率越高越卡"的直接来源。
4. **任何持续动画在 2x 软件渲染下都有固定成本**：一个 14px 齿轮或一个 8px 状态点
   就足以让帧率从 60 掉到 45（本机）。动画的脏区小，但每帧都要走一次 Prism 提交 +
   软件光栅化 + RDP 抓屏编码。
5. 全窗首帧/整窗重绘在 1080p 约 15~35ms（本机），低端机按 3~5 倍放大。

## 三、优化方案

### 3.1 去掉交互热路径上的高斯阴影（P0）

`theme.css`：

- `.input-frame-focused` 删除 `-fx-effect`，保留珊瑚色边框作为聚焦反馈。
- `.sheet-card`、`.card`、`.brand-mark`、`.ai-avatar` 的 `dropshadow` 一并移除
  （`card` 类当前无引用；`sheet-card` 身后已有 55% 遮罩，阴影几乎不可见；
  头像/品牌标只有 24px，平面渐变+圆角已足够）。
- 在 CSS 注释里写明"不要再给输入框/大容器加高斯阴影"，防止后续视觉改版加回来。

### 3.2 仅软件管线开启 ScrollPane 视口缓存（P0）

`MainWindow.setupAutoScroll` 的 skin 监听里按实际管线分流：

- `SWPipeline`：`viewport.setCache(true)` + `CacheHint.SPEED`；
- 其它管线：保持现有 `false`（避免 es2 大纹理上传卡死回归）。

管线探测放 `gui/RenderPipeline`：优先反射
`com.sun.prism.GraphicsPipeline.getPipeline()`（JDK 8 内部 API，反射避免编译期耦合），
失败时回退到 `prism.order` 首项是否为 `sw`。

### 3.3 远程桌面 / 软件渲染下限制渲染倍率（P0）

`Boot` 在 JavaFX 初始化前决策（都可用 `-D` 显式覆盖）：

- `SESSIONNAME` 以 `RDP-` 开头（Windows 远程桌面）：
  - 未显式指定 `MINION_PRISM`/`-Dprism.order` 时，默认 `prism.order=sw`，
    跳过注定失败的 GDI OpenGL 探测；
  - 未显式指定 `-Dglass.win.renderScale` 时，设 `glass.win.renderScale=1`：
    UI 尺寸仍按系统 DPI（`uiScale` 不变，只是不按 2x 超采样光栅化），
    高分屏上像素量降到 1/4，文字略糊但滚动/输入恢复跟手。
- 显式 `prism.order=sw`（例如 `MINION_PRISM=sw`）同样设置 `renderScale=1`。
- 环境变量 `MINION_RENDER_SCALE` 可覆盖（`1`/`1.5`/`2`）。

### 3.4 软件渲染下关闭装饰性连续动画（P1）

新增 `gui/Motion`：`minion.animations=auto|full|reduced`（默认 auto = 软件管线即 reduced）。

- `StatusDot`：running 时不再启动呼吸 Timeline（静态绿点仍表达运行态）。
- `RunningIndicator`：齿轮不转（文案 10s 轮换保留，开销可忽略）。
- `ContextRing`：压缩中不再 60fps 旋转 Canvas，改为静态 300° 弧 + 文案。
- `ConfirmSheet`：遮罩淡入/卡片滑入/淡出直接落终态（一次性省掉约 20 帧全右栏重绘）。

CPU 有富余的用户可用 `-Dminion.animations=full` 恢复动画。

### 3.5 OkHttpClient 懒初始化（P0）

`DeepSeekClient` 构造时不再创建 `OkHttpClient`，首次 `streamChat` 才创建（双重检查）。
`close()` 对未初始化场景安全。这样历史会话恢复不再触发 JDK SSL/JCE 初始化，
首个请求时在会话工作线程支付一次性成本，界面已可见。

### 3.6 会话恢复移出启动关键路径（P1）

`SessionManager` 增加"延迟恢复"构造参数：只建工作空间上下文（毫秒级），
不在构造里恢复历史会话；`restoreAllSessionsAsync()` 在窗口显示后由后台线程执行，
完成后经 `Listener.onSessionsRestored()` 通知 UI 刷新侧栏。

并发安全：

- `WorkspaceCtx.sessions` 改 `CopyOnWriteArrayList`（UI 遍历与后台追加并发安全）；
- `skillCache` 改 `ConcurrentHashMap`；
- `shutdown()` 置 `closed` 标志，恢复循环逐会话检查并回收已建句柄，避免关窗竞态。

同步构造路径保留给单测与基准（默认参数不延迟），行为不变。

## 四、预期收益

| 场景 | 现状 | 优化后 |
| --- | --- | --- |
| 启动到窗口可见（本机，3 会话） | 2.6~3.8 s | 预计 1.6~1.9 s（懒 OkHttp + 异步恢复） |
| 启动到窗口可见（历史多/低端机） | 随会话数线性增长 | 基本与历史量无关，后台渐进恢复 |
| 高分屏输入打字 | 25fps / 单键 80ms | 60fps |
| 高分屏消息区滚动 | 16~25fps | 接近 60fps（视口缓存 + 1x 渲染倍率） |
| 高分屏流式输出 | avg 42ms/帧 | avg 16~26ms/帧 |
| 运行中常驻动画 | 持续 45fps/每帧 21ms | 静态指示，无持续重绘 |

## 五、风险与兼容性

- `renderScale=1` 只影响 Windows 且只在 RDP/显式 sw 时自动启用，可被 `-Dglass.win.renderScale`
  或 `MINION_RENDER_SCALE` 覆盖；GPU 正常机器行为不变。
- 视口缓存在软件管线开启：实测滚动/流式都更快；若后续发现大内容内存问题，可按
  `RenderPipeline` 再收窄。
- 动画降级只影响视觉装饰，不改变任何状态语义（运行中仍有绿点 + 文案）。
- 异步恢复需重点回归：启动期间新建会话、切工作空间、关窗、恢复失败提示。
- JDK 8 兼容；无新依赖。

## 六、验收

- 单测：`RenderPipelineTest`、`BootRenderScaleTest`、`DeepSeekClient` 懒初始化、
  `SessionManager` 延迟恢复（异步完成后会话可见、同步模式不变）。
- `mvn test` 全绿。
- 探针对比：上述 2.2 表的关键项复测。
- 手动：远程桌面 1080p/4K 下打字、滚动、流式、确认卡片、页签状态点。

## 七、实施结果（本机复测，2026-10-31）

`mvn -o test`：1325 用例全绿。

| 场景 | 实施前 | 实施后 |
| --- | --- | --- |
| 启动到窗口可见（3 个历史会话） | 2.6~3.8 s | **1.3~1.5 s**（最小 JavaFX 窗口基线 1.05 s；双击 javaw 1.42~1.48 s） |
| 窗口可见时会话列表 | 已全量恢复（阻塞首屏） | 空列表，约 1.0 s 后后台填充（FX 线程不阻塞） |
| 主窗口输入框打字 @ 2x 渲染倍率 | 97 帧 / 4s，avg 39 ms，max 80 ms | **244 帧 / 4s，avg 15 ms，p95 16 ms** |
| 消息区滚动 @ 2x（缓存关 → 开） | 75 帧，avg 39 ms，p95 143 ms | **229 帧，avg 16 ms** |
| 消息区流式 @ 2x（缓存关 → 开） | 69 帧，avg 42 ms | **145 帧，avg 26 ms** |
| 单个装饰动画 @ 2x | 136 帧 / 45fps | **186 帧 / 60fps**（静态） |
| 软件管线视口缓存/动画降级 | 均未生效 | 主窗口探针：`software=true reducedMotion=true viewportCache=true hint=SPEED` |

说明：2x 是模拟 150% 系统缩放下的 HiDPI 渲染倍率；真实远程桌面会由启动器降为 1x，
上述与倍率相关的收益还会乘以像素量差异（4x 填充量）体现在低端机上。
