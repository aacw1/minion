# 子代理报告落盘、上下文压缩与消息标识 设计

日期：2026-09-13
状态：已实施（2026-09-13；实施回写见 §5 各「实施回写」注记）

## 背景与问题

1. **报告未落盘**：子代理完成时最终报告原样作为 task 工具结果返回主代理，长报告直接膨胀主代理
   上下文；主代理常不得不再自行落盘一份（多一次工具调用，浪费上下文）。
2. **压缩丢内容**：主代理历史压缩后只留摘要，子代理成果细节若未落盘则不可回溯。
3. **子代理无压缩**：`SubAgentLoop` 没有 `ContextManager`，执行长任务（大量工具输出）会逼近
   上下文窗口，超窗报 400 或被截断，且子代理没有用户干预兜底。
4. **子代理过程不可辨**：`SUB_AGENT_DELTA` 事件已产生但 ChatView 未渲染；子代理的思考/正文/
   工具调用/工具结果借用主代理事件通道（混在主代理流里，无编号，4 个并发子代理互相无法区分）。
5. **3 天过期清理与"历史路径回查"契约矛盾**：tmp 目录里工具落盘文件的路径被写进消息历史
   （供未来回溯 Read），但启动时按「修改超 3 天」清理会让历史中的路径静默失效——文件生命周期
   应随会话，而不是按时间。

## 需求（用户确认的决策）

- 子代理报告**总是落盘**（完整报告全文写文件），返回主代理 = **报告前 8000 字符 + 文件路径**；
  短报告全文 + 路径。
- 落盘文件存放在**会话临时目录**（Read 已放行），随会话删除而删除。
- **取消 3 天过期清理**，改为启动时**孤儿目录兜底**（清掉没有对应会话文件的 tmp 子目录）。
- 子代理**按主代理压缩策略自动压缩**：阈值/比例/保留组数与主代理一致，压缩失败走与主代理
  一致的瞬时错误长重试，整个重试流程失败才中止子代理。
- **任务提示词不能压缩**：子代理首条任务消息（`任务: xxx`）压缩豁免（pinned）。
- **压缩器提示词与主代理有区别**：子代理专用压缩指令（强调任务目标与进展、落盘路径）。
- 子代理信息**打印到消息区**（控制台风格区域），统一 `【子代理N】` 前缀标签 + 独立配色，
  加**后缀编号**（会话内递增不复用；工具线程池 4 并发即 1~4 号）。
- **重新加载会话后子代理信息不显示**（子代理事件只进事件流、不写消息历史；重放历史不重演）。

## 方案

### 1. 子代理报告落盘（SubAgentLoop）

- `SubAgentLoop` 构造新增参数：报告落盘目录（会话 tmp 目录，`jarDir/.session/tmp/<会话id>/`）
  与子代理编号；由 `AgentLoop` 在创建子代理时传入。
- `run()` **正常完成路径**（返回最终文本前）：调用
  `OutputDump.write(tmpDir, "subagent-report-" + no, report)`，产出文件名形如
  `subagent-report-1-<ts>-<seq>.txt`（编号在文件名前缀，便于识别）。
- 返回文本格式（`REPORT_MAX_CHARS = 8000`）：
  - 落盘成功且 `报告长度 ≤ 8000`：`报告全文 + "\n\n（完整报告已落盘：<绝对路径>，可用 Read 查看）"`
  - 落盘成功且超长：`报告前 8000 字符 + "\n\n…（完整报告 N 字符已落盘：<绝对路径>，可用 Read 查看）"`
  - 落盘失败（`write` 返回 null）：`报告全文 + "\n\n（报告落盘失败，以上为完整内容）"`——
    降级保成果，不截断。
- **中断/失败路径不落盘**（保持现状：返回"子代理已中断 / 子代理失败: …"短文本）。
- 报告为空（trim 后为空，罕见）时跳过落盘、原样返回，不产生空文件。
- `onSubAgentDone(id, summary)` 的 summary 即上述返回文本（含路径），GUI 渲染"完成"行 +
  可折叠正文（长文本折叠，展开可见报告与路径）。

### 2. 提示词同步（system prompt 与工具描述）

- `SystemPromptBuilder` 第 6 条（task 工具）补充：
  「子代理报告会自动落盘并只返回摘要与文件路径——**不要重复落盘**；需要细节时用 Read 读取
  返回报告中的路径。」
- `TaskTool.description` 同步说明：返回摘要 + 完整报告路径，无需主代理再落盘。

### 3. 清理机制改造（取消 3 天，改孤儿兜底）

- 删除 `OutputDump.cleanup` 与 `OutputDump.RETENTION_MS`，删除 `Main` 启动调用及
  `OutputDumpTest` 中 cleanup 相关用例。
- 新增 `com.minion.core.storage.SessionTempCleaner`：
  - `cleanOrphans(Path sessionRoot, Path tmpRoot, long minAgeMs)`：
    1. 扫描 `sessionRoot/*/*.json`，收集现存会话 id 集合（文件名去 `.json`）；
    2. 遍历 `tmpRoot` 子目录，目录名不在集合中、且目录最后修改时间早于
       `now - minAgeMs` → 递归删除该目录；
  - 目录不存在/扫描失败一律静默（与现状断链容错一致）。
- `Main` 启动时调用：`SessionTempCleaner.cleanOrphans(jarDir.resolve("session"),
  jarDir.resolve(".session").resolve("tmp"), 3600_000L)`。
- 注释明确设计意图：**落盘文件生命周期 = 会话生命周期**；孤儿兜底只覆盖崩溃/删除失败残留，
  正常删除会话/工作空间仍由 `SessionManager` 递归删除（现有行为不变）。

### 4. 子代理上下文压缩

**4.1 抽取公共压缩执行器** `com.minion.core.context.ContextCompressor`

- 把 `AgentLoop.compressWithRetry` 的算法（单次 `ContextManager.compress` + 瞬时错误长重试：
  分类间隔、墙钟 12 分钟、100ms 中断轮询、零降级）抽成可复用类，主代理与子代理共用，
  避免两套策略漂移。
- 形态（实施细节可在计划阶段微调，语义固定）：
  - 构造：`ContextCompressor(RetryPolicy policy)`；
  - `run(ContextManager cm, List<Message> messages, Sink sink)` 返回
    `Result{outcome: OK/NOTHING/FAILED/INTERRUPTED, newMessages, failReason, attempts, elapsedMs}`；
  - `Sink`（调用方注入）：`onRetryProgress(RetryProgress)`（等待/重试期间更新 UI）、
    中断检查（`Thread.isInterrupted`）。
  - 文案仍由调用方决定（主代理保留「压缩失败：…／自动压缩失败：…；本轮已停止」；子代理用
    子代理事件文案），Compressor 只提供 `failReason`。
- `AgentLoop` 改为经 `ContextCompressor` 执行压缩，行为与文案不变（`AgentLoopCompactTest` 回归）。

**4.2 子代理压缩接线**

- `AgentLoop` 创建子代理时（`subAgentRunner` 内）：
  - 主代理 `contextManager == null`（未启用压缩）→ 子代理不压缩；
  - 否则为每个子代理新建 `ContextManager`：
    - `maxContextTokens = 主 contextManager.maxTokens()`；
    - `llm = this.llm`（volatile，切模型后新建子代理用新模型）；
    - `systemTokens = 0`——子代理 `messages` 首条即 system 消息，估算已含，避免重复计数；
    - 压缩指令 = **子代理定制版**（见 4.4）。
- `SubAgentLoop` 每轮请求前（与主代理同位置）：`shouldCompress` → 经 `ContextCompressor`
  压缩；成功替换消息历史并发子代理提示行；`NOTHING` 继续；`FAILED` → 中止子代理，
  返回 `子代理失败: 上下文压缩失败（<原因>）`；中断 → `子代理已中断`。
- 压缩成功提示（子代理事件）：`已压缩上下文（降低至 x%）`。

**4.3 任务消息压缩豁免**

- `SubAgentLoop` 构造时对首条任务消息 `Message.user("任务: " + taskDescription)` 设
  `pinned = true`——`chunkGroups` 天然跳过 pinned 消息，压缩不会吞掉任务描述；
  system 消息本就原样保留（现有 `compress` 语义）。

**4.4 子代理压缩指令（与主代理有区别）**

- `ContextManager` 增加定制压缩 system 指令能力（构造重载 / 字段，默认保持现版
  `COMPRESS_SYSTEM`，主代理行为零变化）。
- 子代理版文案（初稿，实施时定稿）：
  「你是 minion 的子代理上下文压缩器。把对话历史压缩成一段中文摘要，必须保留：当前任务目标与
  验收标准、已完成的步骤与结论、**已落盘文件的完整路径**、遇到的错误与未完成项。只输出摘要正文，
  不要客套，5000 字以内。」

### 5. 子代理事件通道与编号（需求 7）

**5.1 AgentUi 扩展（均为 default 空实现）**

- `onSubAgentStart(int id, String description)`
- `onSubAgentThinking(int id, String delta)`
- `onSubAgentDelta(int id, String delta)`
- `onSubAgentToolCall(int id, String name, JsonObject args)`
- `onSubAgentToolResult(int id, String name, ToolResult result)`
- `onSubAgentDone(int id, String summary)`
- `onSubAgentNotice(int id, String message)`（重试/压缩/中断等过程提示）
- 旧的无编号 `onSubAgentStart(String) / onSubAgentDelta(String) / onSubAgentDone(String)`
  直接改签名删除（项目内实现仅 `SessionController` 与测试 `RecordingUi`，不留双通道）。

**5.2 SubAgentLoop 事件改道**

- 不再调用主代理通道：`onThinking/onContent/onToolCall/onToolResult/onError/onWarning/
  onRetryProgress/onCompressingChanged`；
- 全部改发子代理事件（思考→`onSubAgentThinking`、正文→`onSubAgentDelta`、工具调用/结果→
  `onSubAgentToolCall/ToolResult`、错误/重试/压缩/中断→`onSubAgentNotice`）。
- 子代理重试**不再驱动主代理重试指示器**（并发 4 个子代理互不干扰主 UI）。
- **重试/压缩重试提示节奏（实施回写）**：进入长重试只发 1 条 `onSubAgentNotice`
  （带失败标签与「正在按重试策略自动重试…」），逐次重试不再提示——防 12 分钟长重试把消息区
  刷成数百行；恢复静默（子代理无指示器可复位，用户从后续内容行自然看出已恢复）；
  压缩重试同理只在进入时提示一条。

**5.3 编号分配**

- `AgentLoop` 持有会话级计数器（`AtomicInteger`）；`runSubAgent` 时
  `int id = subAgentSeq.incrementAndGet()`；新会话/重载会话 = 新 `AgentLoop` 实例 → 编号从 1 起。
- 同一时刻并发的子代理编号必然不同；跨批次继续递增（5、6…），历史行无重号歧义。
- 编号同时用于报告落盘文件名。

**5.4 事件结构（EventList / SessionController / ChatView）**

- `EventList.Ev` 增加 `int subAgentId` 字段（0 = 主代理）；新增构造重载，旧调用保持默认 0。
- `SessionController` 新增子代理事件实现：Kind 复用（思考→THINKING、正文→CONTENT、
  工具调用→TOOL_CALL、工具结果→TOOL_RESULT、提示行→WARNING/SYSTEM），`subAgentId` 置位；
  SUB_AGENT_START/DONE 继续使用并带编号；**`SUB_AGENT_DELTA` 删除**（实施回写）——子代理正文
  改走 `CONTENT + subAgentId`，与思考/工具 Kind 复用同一思路，不给正文单独保留 Kind。
- `ChatView` 渲染：`subAgentId > 0` 时标签统一替换为 `【子代理N】`，挂 `log-subagent`
  样式类（theme.css 增独立配色）；思考/正文/工具/结果/提示行均如此；长文本沿用现有折叠机制。
  - START 行：`子任务: <description>`；DONE 行：`完成` + 可折叠报告文本（含落盘路径）。
    （修复轮 1 实施回写：START 仅由 `AgentLoop` 派发时发一次，`SubAgentLoop.run()` 不再重复发
    「任务: <description>」——此前两处各发一次，消息区会渲染两行开始行。）
- **流式身份按子代理隔离（关键）**：现有 `ChatView.stream()` 按"末尾段的 kind 相同即就地更新"
  归并增量——4 个子代理与主代理的思考/正文交错时必然串台（如子代理 A 的 delta 写进主代理的思考段）。
  因此：
  - 流式段身份从 `StreamKind` 扩展为 `(StreamKind, subAgentId)`，`Seg` 增加 `subAgentId`
    字段，`stream()` 判等同时比较两者；
  - `StreamBuffer` 按 `subAgentId` 分组（`Map<Integer, StreamBuffer>`），各流各缓冲；
  - 思考段定稿 `finalizeThinking(subAgentId)`：只定稿该子代理的思考段，避免主代理事件把
    子代理的思考段提前折叠（反之亦然）；
  - 轮次边界（USER_MESSAGE/USER_SUPPLEMENT/TOOL_CALL）按 `subAgentId` 只清对应缓冲，
    子代理的一次 run 内多轮工具回合复用同一隔离语义。
  - **交错流按引用就地合并（实施回写）**：只与"末尾段"判等仍会漏——A 的增量被 B 的段隔开
    后，A 的下一次增量会被误判为新流、另起段并重复整段前缀（4 路并发交错下为常态）。
    落地为 `(owner, kind)` 引用表（`activeStreams`）记住每主人每 Kind 的当前流式段，
    增量原地更新；引用清空时机与缓冲清零对齐。
  - **完成回收（实施回写）**：`SUB_AGENT_DONE` 时删除该主人缓冲与段引用（防会话内条目随
    派发数无界增长）；DONE 行渲染为「完成」摘要 + 可折叠报告正文——长报告不塞单行 Label，
    避免 8000+ 字符超宽截断把末尾落盘路径裁掉。
- **不写历史**：子代理事件只进事件流；`replayHistory` 不重演子代理事件（现状即如此，
  新增测试锁定防回归）。

### 6. 测试

- **报告落盘**（SubAgentLoopTest 扩展或新增）：短报告全文+路径、长报告截断 8000+路径、
  文件名含编号、落盘失败降级返回全文、中断/失败路径不落盘。
- **孤儿清理**（SessionTempCleanerTest）：孤儿目录删除、活跃会话目录保留、
  近期目录跳过、sessionRoot/tmpRoot 缺失静默。
- **子代理压缩**（新增）：阈值触发压缩、任务消息 pinned 保留、压缩失败（重试耗尽）中止并返回
  失败文本、压缩指令随子代理定制版传入（RecordingUi + 记录型 LlmClient 校验
  `completeChat` 的 system 指令）。
- **事件通道**：RecordingUi 记录子代理事件编号与内容，断言主代理通道（onThinking/onContent/
  onToolCall/onToolResult/onRetryProgress）**未被调用**。
- **流式隔离**：按子代理分组的 `StreamBuffer`（各流独立累积）与该 (kind, id) 段身份判等的
  纯函数单测（对齐现有 `ChatViewStreamBufferTest` 风格，不依赖 JavaFX Toolkit）。
- **回归**：`AgentLoopCompactTest`（压缩器抽取后行为不变）、`OutputDumpTest`（移除 cleanup 用例）、
  其余全量测试。

## 非目标

- 不改子代理工具集（task/Skill/AskUserQuestion 仍禁用）。
- 不改主代理压缩阈值、比例、保留组数（0.65 / 0.8 / 6 组）与重试策略参数。
- 不新增 `config.properties` 配置项（截断长度 8000、孤儿宽限 1 小时均为常量）。
- 不做子代理嵌套派发、不做子代理间通信。
- 不做 GUI 上子代理过程的分组折叠/独立面板（仅前缀标签 + 编号区分）。
