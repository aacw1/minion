# 消息区文本选择与复制（设计文档）

日期：2026-08-14 · 状态：已实施

## 背景与根因

消息区正文无法鼠标拖动选择文本、无法直接复制。根因（已确证）：

- 消息全部用 `Label` / `TextFlow` / `Text` 节点渲染（ChatView + BlockNodeFactory），
  而 JavaFX 平台本身不支持这些节点拖选文本（`Label` 无选中能力，`TextFlow` 从未内置 selection），
  代码因此在 [ChatView.java:165](../specs/../../src/main/java/com/minion/gui/chat/ChatView.java#L165) 以
  「右键菜单复制 + 双击复制全文」作为替代途径——这是设计取舍，不是回归。
- 本机 Zulu 8u502 的 jfxrt.jar 实测：`TextFlow.hitTest`/`Text.hitTest` 公开 API 不存在
  （自实现 TextFlow 选中只能走 `com.sun.javafx` 内部 API，`impl_hitTestChar`/`impl_selection*`）。

## 方案（用户已确认）

**消息文本改渲染为只读 `TextArea`（纯文本）**，依赖 TextArea 原生能力：
鼠标拖选高亮、Ctrl+C、双击选词、右键菜单（复制/全选）——零自研选中逻辑，最稳定。

代价（已接受）：markdown 富文本样式（粗体/行内代码着色/表格边框）不再渲染，
正文退化为纯文本展示。通过现有 MarkdownRenderer 把 markdown 展平为**可读纯文本**
（去掉 `**`、`` ` `` 等语法记号），而非直接展示源码。

## 改动点

### 1. MarkdownRenderer 新增纯函数 `toPlainText(String md)`（可单测）

复用现有 `parse()`，块 → 纯文本展平规则：

| 块类型 | 展平规则 |
|---|---|
| PARAGRAPH | spans 文本直接拼接（span.text 已含软换行） |
| HEADING | text |
| CODE | text（保留原内容与换行，不加围栏） |
| LIST | 每项 `"• "` 前缀 + 换行 |
| QUOTE | text |
| TABLE | 每行单元格 `" | "` 连接 + 换行 |
| RULE | 忽略 |

块之间空行（`\n\n`）分隔，整体 trim。行内样式（bold/italic/code/strike）只取文本，语法记号消失。

### 2. 新组件 `MessageTextArea`（gui/chat 包内）

`TextArea` 子类，解决两个平台问题：

- **外观**：只读、`setWrapText(true)`、样式类 `msg-textarea`（CSS 见第 3 点）——
  透明内部（.content/.scroll-pane/.viewport）、去焦点环、选中高亮色、LCD 字型平滑。
- **自动高度（关键）**：TextArea 的 prefHeight 由 `prefRowCount`（默认 10 行）决定，
  不随内容变化。重写
  `computePrefHeight(width, top, right, bottom, left)`：
  用内部 `Text` 测量器（同字体、wrap 宽度 = width − 水平 padding），
  返回 文本高 + 垂直 padding + 小余量。宽高完全融入 VBox 布局，
  无需手动 listener，窗口缩放自动重排。
- 右键菜单/双击选词/Ctrl+C 全用 TextArea 原生行为，不挂任何自定义鼠标处理器。

### 3. ChatView 消息渲染改造

| 事件 | 现状 | 改为 |
|---|---|---|
| USER_MESSAGE | Label(msg-user) + makeCopyable | MessageTextArea(msg-user + msg-textarea)，raw text |
| USER_SUPPLEMENT | Label(msg-user) | tag Label + MessageTextArea |
| THINKING | Label 流式重建 | MessageTextArea 流式**就地 setText** |
| CONTENT | VBox + BlockNodeFactory 富文本块，流式重建 | MessageTextArea 流式就地 setText(toPlainText(md)) |
| 系统行（TOOL 卡片/TOOL_RESULT/ERROR/WARNING/STATS/SYSTEM/子任务） | Label/card + makeCopyable | **不变**（辅助信息行，保留右键+双击复制） |

- `makeCopyable` 不再挂在消息 TextArea 上（原生能力取代；且原双击复制与
  TextArea 原生双击选词冲突，必须移除）。
- 流式哨兵 `STREAMING_MARK` 保留：同一流式流（thinking 或 assistant）**就地更新文本不重建节点**
  （不丢焦点/选中态）；流式类型切换（thinking → content）仍按现有语义替换节点。
- `BlockNodeFactory` 富文本渲染路径保留（不被删除），仅 ChatView 不再调用；
  `makeCopyable` 保留给系统行。

### 4. theme.css

```css
/* 消息只读 TextArea 公共样式 */
.msg-textarea {
    -fx-highlight-fill: #3b6fe0; -fx-highlight-text-fill: #ffffff;
    -fx-focus-color: transparent; -fx-faint-focus-color: transparent;
    -fx-font-smoothing-type: lcd;
}
.msg-textarea .content { -fx-background-color: transparent; -fx-padding: 0; }
.msg-textarea .scroll-pane { -fx-background-color: transparent; }
.msg-textarea .scroll-pane > .viewport { -fx-background-color: transparent; }
```

`msg-user` / `msg-assistant` / `msg-thinking` 现有背景/圆角/padding 规则对 TextArea 同样适用，
与 `.msg-textarea` 叠加即可。

## 长消息展开 Bug 修复（目验反馈后）：Parent.prefHeightCache 缓存旧值

目验反馈：「有些还是只有一行，有些多行但没完全撑开，还是有滚动条」——
长消息（约 10 行以上）被压缩到约 197px 并出现内部滚动条，短消息正常。

### 根因（探针 6→17 实证链定位）

1. **TextArea 默认 prefHeight**：`TextAreaSkin.computePrefHeight` 按 `prefRowCount=10`
   返回固定 ≈197px，与内容无关；只有 `prefHeightProperty == -1`（USE_COMPUTED_SIZE）时走到该路径。
2. **Parent.prefHeightCache 缓存**：`Parent.prefHeight(-1)` 把 `computePrefHeight(-1)` 结果
   缓存进私有 `prefHeightCache`（cache==-1 才重算）。`Region.prefHeight(width)` 是 final：
   `getPrefHeight()==-1` 时走 `Parent.prefHeight(width)`（width!=-1 实时计算不缓存，
   width==-1 则**进缓存路径**）。
3. **HBox 布局早期用 -1 测高**：HBox.computePrefHeight → `computeChildPrefAreaHeight(child, -1.0, …)`
   → `child.prefHeight(actualWidth)`。多段场景下布局第一趟在 TextArea 拿到显式 prefHeight **之前**
   就调用了 `prefHeight(-1)` → 把 skin 默认 197px 写进 HBox.prefHeightCache。
4. **requestLayout 传播阻断**：之后 relayout() 的 `setPrefHeight` 触发 requestLayout，
   但子节点在父 HBox `performingLayout` 期间请求布局**不向上传播**
   （`markDirtyLayout(false)` 仅在 `!getParent().isPerformingLayout()` 时传播）→
   `clearSizeCache()` 永不执行 → VBox 持续按缓存旧值 197px 压缩长消息。
5. **决定性验证**：反射重置 HBox.prefHeightCache 后 `prefHeight(-1)` 立即从 174 恢复 325（探针 15）。

### 修复（探针 18 验证：5 段全部正确展开）

MessageTextArea **构造时立即测量并设置显式 prefHeight**（宽度未定用兜底 600px，
宽度监听随后用真实宽度校正）：

```java
private static final double FALLBACK_WIDTH = 600;
// 构造函数末尾：
relayout(); // 构造即设置显式 prefHeight，永不给 Parent.prefHeightCache 留旧值
// relayout() 内：
if (width <= 0) width = FALLBACK_WIDTH;
```

要点：`prefHeightProperty` 从构造起恒为显式值（≠-1）→ `Region.prefHeight` 的
`-1.0 → Parent 缓存` 路径永不进入 → HBox/VBox 布局永远拿到正确内容高度。
短消息（<197px）此前不受影响的原因：布局时它们的显式高度已算出，未踩到缓存。

### 防回归

- 类 javadoc 已记录根因与修复（MessageTextArea 顶部注释，含「重置缓存后立即恢复」实证）。
- 以后改高度逻辑时不得把 prefHeight 恢复为 USE_COMPUTED_SIZE 交由布局计算——那是本 Bug 的入口。

## 长消息展开 Bug 修复二（目验反馈后）：ScrollPane 压缩 + wrap 槽位死锁

用户再次目验反馈「还是不行」。上一节修复（构造即设显式 prefHeight）在隔离探针环境验证通过，
但真实应用（真实 CSS + ScrollPane + 流式）仍有长消息压缩。探针 19-28 复现并定位**两处新根因**：

### 根因 A：ScrollPane fitToHeight 按 content.minHeight 压缩消息区（探针 19-20 实证）

- `ScrollPane fitToHeight=true` 布局时 content 高度 = `boundedSize(视口高, content.minHeight, content.maxHeight)`，
  判定用的是 **minHeight**。VBox 默认 minHeight = 各段最小值之和（TextArea minH≈1-2 行，5 段仅 213px）。
- 内容多时 content 被压到视口高（698px）→ VBox 空间不足**压缩 children** → 长段（prefH=910）被压到 522px
  → TextArea 内部出现滚动条。实证：`viewport=698 contentH=698 contentMinH=213`，box3 持续 522 不收敛。

### 根因 B：measurer wrap 宽度与内部实际 wrap 差 12px → 滚动条自反馈死锁（探针 23-24 实证）

- TextArea 内部文本 wrap 宽度 = 控件宽 − 内部 ScrollPane 边框（1px×2）− 垂直滚动条（10px，主题设置）= **868**；
  measurer 用 `width − padding` = **880**。差 12px。
- 行内容恰在 wrap 临界（每行 57-58 字符 ≈ 容量）→ 12px 差异致内部实际行数比 measurer 多 4 行
  → 内容 589 > 测量高度 556 → **滚动条出现 → wrap 更窄 → 行更多 → 滚动条保持**（自反馈死锁，
  高度永不追上内容）。

### 修复（双管齐下，探针 25-28 全场景验证：box3H=973=prefH 精确、vbar=false）

1. **ChatView（VBox）覆写 `computeMinHeight = computePrefHeight`**：
   boundedSize 在内容多时取 prefH 自然展开、内容少时取视口高保持铺满（fitToHeight 语义不变，
   探针 21 场景 B 验证铺满保留）。
2. **MessageTextArea 保守测量 + 布局后精校**：
   - measurer wrap 宽度预留 INNER_SLOT=12（边框+滚动条槽位）→ 测量恒 ≥ 内部实际 → 滚动条不出现；
   - 布局后（双 runLater 保证在布局 pass 之后）读内部 Text 节点（skin 实际渲染）的真实高度
     `setPrefHeight` 精校——消除保守测量的空隙与临界 wrap 行差（探针 28 收敛链：476→555→910→973）。

### 防回归

- MessageTextArea 类 javadoc 记录「三道防线」：①构造即显式 prefHeight（防 Parent 缓存旧值）
  ②保守窄 wrap 测量（防滚动条自反馈死锁）③布局后精校（防空隙/临界行差）。
- ChatView.computeMinHeight 注释记录根因 A（勿删：删掉后 ScrollPane 重新压缩消息区）。
- 改动滚动条宽度/内部边框的 CSS 时，INNER_SLOT 需同步校准（当前 10px 滚动条 + 2px 边框）。

## 长消息展开 Bug 修复三（目验反馈后）：流式期间行高比低估 → 滚动条全程可见

用户再次目验反馈：「多行变一行，或者多行但还有滚动条，有的多行没有滚动条，不稳定」。
上一节修复在静态场景（一次性 setText）验证通过，但流式输出期间仍有滚动条。探针 29-31 定位根因：

### 根因 C：TextAreaView 内部 Text 行高 ≠ 普通 Text 行高（探针 29-31 实证）

- TextAreaView（skin 实际渲染文本的节点）的**每行行高 ≈ 普通 Text 节点的 1.0686 倍**
  （探针 31 在 22 行/42 行处比值完全一致；14px Microsoft YaHei，同字体/同 wrap/同 lineSpacing）。
- measurer 是普通 Text → 流式期间每次测量都**低估约 6.86% 的行高** → prefH 恒小于真实内容
  → 内部滚动条出现 → wrap 变窄 → 行数更多 → 内容更高（滚动条自反馈）→ vbar 全程可见。
- 布局后精校虽然能读到精确 innerH，但：①校正只在布局后的 runLater 执行，流式高频 setText
  下追赶不及；②**更致命**——校正读取 innerH 时若布局还没用「当前文本」跑过（流式窗口期），
  读到的是旧文本的高度，`setPrefHeight(exact)` 会把新高度**覆盖回旧值**
  （探针 29 实证 box3H 持续落后 innerH 24-141px，FINAL 才收敛）。
  `inner.getText().equals(getText())` 检测无效：skin 的文本属性是同步更新的，恒等。

### 修复（探针 31 重跑验证：流式全程 vbar=false、prefH 恒 ≥ innerH）

1. **行高比补偿**：relayout 测量结果 × `lineScale`（初始 1.07 = 实测 1.0686 取整），
   prefH 从第一步就 ≥ 真实内容 → 滚动条永不出现 → wrap 稳定 → 测量稳定。
2. **行高比自适应**：校正时 `lineScale = innerH / measurerH` 实时自校准（随字体变化自适应，
   而非硬编码 1.0686）。
3. **布局新鲜性检测**（替换无效的文本比对）：`innerH / measurerH` 必须落在
   `[lineScale-0.03, lineScale+0.05]` 区间才算「布局已用当前文本跑过」——旧文本布局的比值
   会显著偏小 → 跳过本次精校、下轮重试，杜绝旧高度覆盖新高度。

### 防回归

- lineScale 的取值依据（1.0686@14px YaHei）记录在字段注释；改动全局字号/字体时
  自适应机制会自动校准，无需手动改常量。
- 布局新鲜性检测的阈值（±0.03/0.05）须大于流式窗口期旧文本布局的比值偏差、小于
  行高比本身的真实浮动；两处探针实测均落在 1.0686 附近，余量充足。
