# minion 消息区滚动卡顿治理（截断保活 200 段）设计

日期：2026-08-16
状态：待用户审查

## 背景

长会话（数千条消息、几万行文本）时消息区滚动变卡。根因：ChatView 是 VBox 无上限平铺所有消息段——每段 = HBox（Label + MessageTextArea），而 MessageTextArea 内部还有 skin 节点树、测量器与布局后精校（双 runLater）逻辑。节点数随消息线性增长，ScrollPane 滚动每帧需对全部节点重新布局，卡顿随会话变长加剧。

## 方案（用户确认：按消息段条数截断，上限 200 段）

「按行数截断」被否决：行数是动态值（依赖 wrap 宽度，窗口缩放即变），需为每段维护行数计量并动态核算截断边界，复杂度高。「循环队列」被否决：500/200 规模下 `ArrayList.remove(0)` 与 O(1) 删除无可感知差异，保持现有形态改动最小。

### 1. 显示层截断（核心）

- ChatView 新增常量 `MAX_SEGS = 200`。
- `append()` 尾部追加后检查：`segs.size() > MAX_SEGS` → 移除头部 `size - MAX_SEGS` 段，`segs` 与 `getChildren()`（每段一个 HBox，顺序对齐）同步删。
- 截断只发生在 `append()`（新段产生路径：用户消息/补充/工具/系统行/流式首段/会话重放）；流式就地更新（THINK/REPLY 末段 setText）不新增段，不触发截断。
- 流式段只在尾部就地更新 → 截断只动头部，永不误删正在流的段。

### 2. EventList 不动

EventList 是纯内存字符串缓冲（未激活会话暂存）。保留全量；切换会话 `bind(true)` 重放时，ChatView 的 append 截断同样生效，只渲染最近 200 段。重放全部存量有一次性 CPU 开销，可接受（瞬时）。

### 3. 滚动位置补偿（防历史区视口跳动）

截断发生在头部 → 内容总高变小。分两种状态：

- **贴底**（policy.shouldFollow）：新事件自然触发 scrollBottomRequest 置底，无感，无需处理。
- **停在历史区**：vvalue 是归一化比例，内容变矮后同一 vvalue 对应的绝对位置下移 → 视口跳动。

补偿：ChatView 新增可注入回调 `setTrimListener(DoubleConsumer)`（与 `setScrollBottomRequest` 同款注入方式），截断时回调，参数为被删段高度合计 removedH。**先删节点、后回调**：MainWindow 计算时"当前内容高度"即截断后高度。

```
removedH = 回调参数（被删段高度合计）
H_old = 当前内容高度 + removedH（截断后内容高度 + 被删部分 = 截断前高度）
v' = clamp(v × (H_old − viewport) / (H_old − removedH − viewport), 0, 1)
chatScroll.setVvalue(v')
```

贴底（v≈1）时 v'≈1 自然收敛，公式统一处理，无需分支。

## 实施落点

- [ChatView.java](src/main/java/com/minion/gui/chat/ChatView.java)：`MAX_SEGS` 常量；`append()` 尾部截断；`setTrimListener` 注入；被删段高度合计后回调。
- [MainWindow.java](src/main/java/com/minion/gui/MainWindow.java)：`onSessionActivated` 中随 `setScrollBottomRequest` 一起注入 trim 回调，做 vvalue 补偿。

## 测试

1. 截断为 JavaFX 节点操作，项目无 TestFX 设施，手工验证清单：
   - 长会话（>200 段）滚动流畅；200 段后新增消息时头部消息消失
   - 贴底跟随：流式输出时始终贴底，无跳动
   - 历史区停留：新增消息时视口不跳动（补偿生效）
   - 流式输出期间截断：正在更新的末段不受影响
   - 切换会话重放：只渲染最近 200 段
2. 全量 `mvn test` 回归。

## 影响面

- 仅 ChatView/MainWindow 两处；不改事件流、不改消息历史（EventList 全量保留）、不改落盘。
- 历史消息截断仅影响显示层：滚动到顶也看不到第 200 段之前的内容（可接受的取舍，后续如需可加"加载更早"）。
