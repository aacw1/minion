# 大输出入历史闸门与压缩防抖设计

日期：2026-09-14
状态：已确认（2026-09-14，用户批准"按推荐继续"；待定项按推荐值定稿）
来源：本次「反复压缩、卡在 78-82% 无法继续」事故的系统化调试（根因已定位并复现）

## 1. 背景与问题

### 1.1 事故现象

执行任务时反复触发自动压缩，每次提示"上下文降低至 78-82%"，短暂继续后又压缩，流程无法推进。

### 1.2 根因链（已定位并复现）

1. **大输出无上限入历史**：工具结果写入 `session.messages` 前只有空输出占位（`ToolResult.outputForApi`），**无任何字符级兜底**（2026-08-23 工具输出截断设计只覆盖了 Bash/Grep/Db 各自的返回，未覆盖"模型随后把内容读回来"的通道）。
2. **两条无上限回读通道**（本次事故直接触发源：SQL 一次查询返回 28 条大 JSON 记录）：
   - `DbTool` 单次结果 ≤ 30000 字符（超限落盘），但落盘提示原文是"可用 Read 查看"——**引导模型去读全量**；
   - `ReadTool` 默认 `limit=2000` **行**，**无字符上限、无单行截断**（GrepTool 有单行 1000 字符截断，ReadTool 没有）→ 模型 `Read` 落盘文件一次即全量进历史；`full=true` 还可反复重查（每次 ≤30k 字符，28 次累计最多 840k 字符）。
   - 放大因素：30000 字符若含中文，按 TokenCounter（中文 0.7 token/字）≈ 21000 token，单次即不小。
3. **大 tool 结果全落在"最近 6 个原子组"保留区**：`ContextManager` 的原子组 = `assistant(tool_calls) + 其后全部 tool 结果`，最新的大结果组必然在保留区内。
4. **压缩永远压不到阈值以下**：`KEEP_RECENT_GROUPS=6` 是硬下限且**无 token 预算**；`takeCount` 目标量为固定 `max×0.65×0.8`，不校验"压缩后是否低于阈值"。保留区超阈值时压缩无解。
5. **无防抖**：`AgentLoop` 循环顶每轮请求前检查 `shouldCompress`，压缩后仍 ≥ 阈值 → 下一轮立即再压 → 每轮白付一次压缩 LLM 调用（几十秒），并谎报"已压缩"。

### 1.3 复现证据（脚本模拟现行算法，200k 模型）

| 场景 | 结果 |
|---|---|
| 一次并行 28 个 SQL（1 组 ≈140k token） | 压缩后 **76.1%**，此后每轮触发压缩，`take=1`，压缩后 76.1%→76.1%→…（收益为 0，每次都调 LLM） |
| 每轮 4 个并行 SQL，共 10 轮 | 第 7 轮后**每轮都压缩**，压缩后 65.9% 仍超阈值 → 下轮又压 |

与用户现象（78-82% 来回）量级一致。

## 2. 目标与非目标

### 目标

1. **统一入历史闸门**：任何工具结果写入历史前长度受控（阈值 30000 字符，与 Bash/Grep/Db 同口径）；超大内容落盘留档，历史只放头部 + 路径 + 可操作的续读提示。
2. **防套娃**：读取类工具（Read/Grep/Glob）超限只截断 + 分页续读提示，**不二次落盘**，保证"永远读得到全文、永远有下一步"。
3. **SQL 侧拆分引导**：DbTool 落盘提示改为"数据量过大，请拆分查询"，不再引导无脑 Read 全量。
4. **压缩无效防抖 + 如实提示**：压缩后仍 ≥ 阈值 → 本回合不再自动压缩，如实告知用户并给建议；不再谎报"已压缩"。

### 非目标

- 不改压缩算法本身（保留区 token 预算化/大结果折叠列为后续可选项，见 §7）；
- 不做事后折叠已入历史的内容（避免改写已发送前缀导致供应商 prompt cache 失效）；
- 不改 GUI 渲染（`ui.onToolResult` 仍收原始结果，界面展示不变）；
- 不改 Bash/Grep 既有截断逻辑（仅新增闸门兜底）；不改 Grep 的落盘行为（其落盘文件被 Read 读取时走 Read 的分页规则）。

## 3. 方案设计

### 3.1 统一入历史闸门（新类 `ToolOutputGate`，core/tools）

```java
public final class ToolOutputGate {
    public static final int MAX_CHARS = 30000;         // 入历史单条上限（与 Bash/Grep/Db 同口径）
    private static final Set<String> READ_TOOLS =     // 读取类：截断不落盘（防套娃）
            new HashSet<>(Arrays.asList("Read", "Grep", "Glob"));
    /** 返回可写入历史的字符串：未超限原样；超限按工具类截断/落盘并附提示 */
    public static String apply(String toolName, String output, Path tmpDir) { ... }
}
```

- **生产类**（其余全部工具，含 SQL/Bash/MCP/浏览器）：超限 →
  `头部 30000 字符` + `…（输出过大已截断：共 N 字符，完整内容已落盘：<绝对路径>；可用 Read 分页查看，或改用更精确的查询/参数）`。
  落盘复用 `OutputDump.write(tmpDir, "tool-" + 工具名, output)`；`tmpDir == null` 或落盘失败 → 降级纯截断提示（不阻断）。
- **读取类**（Read/Grep/Glob）：超限 →
  `头部 30000 字符` + `…（内容超单次上限（30000 字符）已截断，原内容共 N 字符；请用 offset/limit 分页继续读取）`。**不落盘、不产生新文件**（杜绝"读→落盘→再读→再落盘"套娃）。
- 设计上读取类主要由工具自身自限（Read 见 §3.2；Grep 已有 30000/单行 1000；Glob 200 条），闸门是双保险。

**接线点**（两处，均在写入 `session.messages` 前）：
- `AgentLoop.java` 工具结果入历史处（现 656 行 `Message.toolResult(...)`），用 `sessionTmpDir`；
- `SubAgentLoop.java` 同处（现 212 行），用 `reportDir`。
- `ui.onToolResult(name, result)` **保持传原始 result**（GUI 不变）；仅入历史字符串受闸门处理。

### 3.2 ReadTool 自限（分页续读，不落盘）

现状：`limit` 默认 2000 行，无字符上限、无单行截断。新增：

- 常量：`MAX_OUTPUT_CHARS = 30000`（单次输出字符上限）、`MAX_LINE_CHARS = 2000`（单行截断）。
- 逐行累积输出，累计将超上限时停止；尾部提示：
  `... 单次输出上限 30000 字符，已显示第 A-B 行（共 N 行）；请用 offset=B+1 继续读取`；
  未达上限但未读完时保留现有提示（`... 共 N 行，已显示 M 行（可用 offset/limit 翻页）`）。
- 单行超 `MAX_LINE_CHARS`：截断该行 + 后缀 `…[本行超长，共 M 字符已截断]`（后缀计入上限；代理对边界对齐 `TruncatedOutput` 既有口径）。
- 保证：**两页拼接 == 原文对应行区间**（测试断言"分页可读完"），续读 offset 明确。

### 3.3 SQL 侧拆分提示

- `MarkdownTable.fit` 超预算提示改为：
  `…（结果过大：共 N 字符，完整内容已落盘：<路径>。请拆分查询（加 WHERE/LIMIT 缩小范围、分页或分列查询），需要全文可用 Read 分页查看）`
- `DbTool.description()` 补充引导：避免一次拉取大量大字段（如整表 JSON 列），建议按需 WHERE/LIMIT 拆分。
- inline 预算 `CHAR_BUDGET` 维持 30000（与其它工具同口径；闸门已兜底）。**备选**：降为 12000 让"拆分提示"更早出现——待审定时确认（见 §9 待定项）。

### 3.4 压缩无效防抖（AgentLoop / SubAgentLoop）

- 新增回合内标志 `compressIneffectiveThisTurn`；`runUserTurn` 开头重置。
- 压缩成功（OK）后立即复查 `shouldCompress(session.messages)`：
  - 仍为 true → 置标志 + `onWarning("自动压缩后上下文仍占 X%（大输出占满保留区，无法继续压缩）；本轮不再重复压缩，建议新建会话或缩小任务范围")`；
  - 提示文案不再出现"已压缩降低至 X%"的误导表述（X 仍超阈值时）。
- 循环顶触发条件追加 `&& !compressIneffectiveThisTurn`；手动 `/compact`（`compactNow`）**不受防抖限制**（用户显式操作仍执行）。
- 防抖后本轮继续请求（可能超窗 → 服务端报错兜底，与现设计一致；提示已提前告知用户）。
- `SubAgentLoop`：同规则（压缩后仍超阈值 → 不再重复压缩，任务继续；压缩失败仍按现行规则中止）。

## 4. 边界与错误处理

- `output == null`/空：不受闸门影响（空输出占位逻辑在前，保持现状）。
- 闸门阈值恰好等于长度：不截断（`<=` 原样返回）。
- 落盘失败/tmpDir 为 null：降级为纯截断 + 提示（说明完整内容未能留档，建议缩小查询/参数），不阻断工具主流程。
- 截断点落在代理对中间：回退一位（对齐 `MarkdownTable.cell`/`OutputDump` 口径）。
- 旧会话恢复不受影响：闸门只作用于新入历史的消息；历史中已存在的超大消息不做事后改写（避免缓存失效）。
- 落盘文件生命周期 = 会话生命周期（`OutputDump` 既有约定，删会话时清理），路径稳定可反复分页读取。

## 7. 风险与兼容性

- **模型可能不理睬分页提示反复读**：属提示词引导问题；压缩与防抖兜底，最坏情况退化为现状（不劣化）。
- **"读全文必然占上下文"是物理约束**：闸门不消除它，只让模型按需分段读；全局消化大内容引导走子代理（Task）/脚本（Grep/head/jq）路径（写入提示文案与 description）。
- **额外工具轮次成本**：分页读多几次调用，远小于每轮重复携带超大历史的代价。
- **既有测试断言**：Db/Bash/Grep 文案改动需同步更新断言（已列入测试计划）。
- **未做的事后折叠**：历史中早先已进入的超大消息仍可能触发死循环 → 由 §3.4 防抖兜底（不再卡流程，但提示用户新建会话）。彻底解决见 §7.1。

### 7.1 后续可选项（本次不做，留待评估）

- 压缩算法保留区 token 预算化（允许压缩"最老的超大保留组"）；
- 对已入历史的大结果做"内容级折叠"（会改写已发送前缀，需评估 prompt cache 影响）；
- DbTool inline 预算下调（30000 → 12000）让拆分提示更早出现。

## 8. 验收

1. `mvn compile` + `mvn test` 全绿；
2. 手工验收：
   - 构造超大工具输出（如 SQL full 查询/大文件）→ 历史只见头部 + 落盘路径，进度圈不暴涨；
   - Read 读大文件 → 分页续读能读完全文，无二次落盘文件产生；
   - 注入"压缩后仍超阈值"场景 → 只出现一次防抖提示，不再每轮压缩；
   - 原始 GUI 展示（工具详情）行为不变。

## 9. 待定项（已定稿：按推荐值）

1. `ToolOutputGate.MAX_CHARS` = **30000**（与 Bash/Grep/Db 同口径）；
2. DbTool inline 预算 **维持 30000**（闸门兜底；降为 12000 的方案不采纳）；
