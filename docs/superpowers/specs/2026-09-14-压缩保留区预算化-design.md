# 压缩保留区 token 预算化设计

日期：2026-09-14
状态：已确认（2026-09-14；用户选定方向 A + 组数上限放开；**二次修正**：防抖改为 v2 响应式收益门槛——用户指出"回合内只能用一次"会卡死长任务，2026-09-14 采纳 v2）
来源：承接《大输出入历史闸门》设计——闸门已从入口限制单条大输出，但**保留区（最近若干原子组）无 token 上限**这一残余根因未除

## 1. 背景与问题

### 1.1 残余根因

`ContextManager` 的压缩算法为「按原子组从最早压到 `0.65×0.8` 目标量，且硬性保留最近 6 组」：

```java
int maxTake = groups.size() - KEEP_RECENT_GROUPS;              // 6 组硬下限
long compressTokens = max × THRESHOLD × COMPRESS_RATIO;        // 固定目标量
```

问题：**6 组下限只看组数、不看大小**。若最近几组含大输出（一轮并行 28 个 SQL = 同一原子组），保留区自身即可超过 65% 阈值，压缩永远压不到阈值以下：

- 压缩后 `estimate` 仍 ≥ 阈值 → `AgentLoop` 下一轮请求前又触发压缩 → 每次白付一次压缩 LLM 调用（几十秒），收益 ≈ 0；
- 现状由「压缩无效防抖」（2026-09-14 闸门设计第 4 节）兜底：**不再重复压缩 + 如实提示**，但用户仍卡在「上下文占用高、无法继续推进」。

闸门（单条 ≤ 30000 字符）解决了「单条」过大，但**同一原子组内多条 tool 结果的合计**仍可远超阈值，且原子组在协议上不可拆（`assistant(tool_calls)` 与其 tool 结果必须同进同出）。

### 1.2 目标

1. 保留区改为**按 token 预算自适应**（不再固定 6 组），使压缩在绝大多数场景下能一次压到阈值以下；
2. 保留区预算内**尽量多保留近期组**（近期细节对模型更有用）；
3. 极端场景（最新 1 组自身超预算、或常驻内容占满）仍有明确、可预期的兜底行为，不空转。

### 1.3 非目标

- 不做组内折叠（截断组内 tool 内容）：会改写历史消息内容，且组仍是协议原子单位，本轮不引入；
- 不改压缩指令/摘要上限（5000 字）、不改防抖语义、不动配置项（`config.properties`）与 GUI；
- 不改 `chunkGroups` 分组规则（tool_call↔tool 配对保证不变）。

## 2. 设计

### 2.1 常量（`ContextManager`）

| 常量 | 值 | 说明 |
|---|---|---|
| `KEEP_BUDGET_RATIO`（新） | `0.2` | 保留区预算 = `maxContextTokens × THRESHOLD × KEEP_BUDGET_RATIO` = **0.13×max**（200k → 26k token）。语义：触发量（0.65×max）的 20% 留给保留区，80% 为压缩目标（沿承 `COMPRESS_RATIO = 0.8` 的分配意图，改为单向约束） |
| `KEEP_MIN_GROUPS`（新） | `1` | 最新 1 组**无条件保留**（哪怕自身超预算）——当前任务上下文不可丢 |
| `MIN_COMPRESSIBLE_RATIO`（新） | `0.05` | **事前收益门槛**：可压量 ≥ 5%×max 才值得压缩（200k → 10k token）。低于门槛跳过本次（不调 LLM、不设禁止标志）——摘要输出本身要 ~2-3.5k token，压少了净收益为负 |
| `FORCE_COMPRESS_RATIO`（新） | `0.85` | **危险区豁免**：`estimate ≥ 85%×max`（贴近窗口）时无视事前门槛强制压缩，尽量腾空间保命 |
| `KEEP_RECENT_GROUPS` | 删除 | 6 组硬下限取消（组数上限也取消：预算内尽量多留） |
| `COMPRESS_RATIO` | 删除 | 「压缩量至少 0.8×阈值」的目标不再需要：保留区 ≤ 0.13×max 天然保证压缩力度（触发时历史 ≥ 0.65×max，压后 ≈ 常驻 + 摘要 + 保留区） |

### 2.2 算法：保留区计数

```java
/** 保留的原子组数：从最新组往前累加，累计 ≤ 预算的最大组数（下限 KEEP_MIN_GROUPS=1，无上限） */
private int keepCount(List<List<Message>> groups) {
    long budget = (long) (maxContextTokens * THRESHOLD * KEEP_BUDGET_RATIO);
    long acc = 0;
    int keep = 0;
    for (int i = groups.size() - 1; i >= 0; i--) {
        long t = TokenCounter.estimateMessages(groups.get(i));
        if (keep >= KEEP_MIN_GROUPS && acc + t > budget) break;
        acc += t;
        keep++;
    }
    return Math.max(keep, KEEP_MIN_GROUPS);
}
```

`compress(messages)`：

1. `groups = chunkGroups(messages)`（规则不变：summary/pinned/system 跳过；`assistant(tool_calls)` + 其后 tool = 一组）；
2. `keep = keepCount(groups)`；`take = groups.size() - keep`；
3. `take <= 0` → 返回**同一引用**（无可压缩：不调 LLM、不改历史）；
4. 否则把 `groups[0, take)` 全部并入摘要（旧摘要拼入输入，新摘要 ≤ 5000 字），保留 `groups[take, end)`——结构与原实现一致（system 原样在最前、新摘要置前、pinned 原样、未压缩组按序）。

**事前收益输入（供 2.4 门槛判定）**：

```java
/** 本次压缩能压掉的 token 量（＝将被并入摘要的组合计；take = 0 时为 0） */
public long compressibleTokens(List<Message> messages) {
    List<List<Message>> groups = chunkGroups(messages);
    int take = groups.size() - keepCount(groups);
    long acc = 0;
    for (int i = 0; i < take; i++) acc += TokenCounter.estimateMessages(groups.get(i));
    return acc;
}
```

### 2.3 行为变化

| 场景 | 旧行为 | 新行为 |
|---|---|---|
| 最近 6 组含大组（如 2 组共 100k token） | 压不掉，压后仍 76% → 每轮重复压缩（防抖兜底） | 保留区预算 26k → 只保底留最新 1 组；压后通常 < 阈值 → 提示「降低至 X%」 |
| 近期组都很小（每组 <1k token） | 保留 6 组 | 预算内尽量多留（26k 可容十几~几十组），近期细节更完整 |
| 单个最新组自身 > 0.13×max | 无差别（硬留 6 组） | 保底留 1 组；可压量长期不足 → 事前门槛跳过（不调 LLM）+ 提示一次（见 2.4） |
| 常驻内容（system + pinned + 摘要）占满 | 每轮空走一次压缩检查 | 事前门槛直接跳过（无 LLM 调用）+ 提示一次（见 2.4） |

压缩频率显著降低（一次压到保留区预算内），单次压缩力度更大；摘要仍为单条 ≤ 5000 字（旧摘要合并）。

### 2.4 压缩触发与「压不动」的处理（v2 响应式收益门槛，2026-09-14 二次修正）

**修正缘由**：初版（已实施的 v1）把「压缩无效」记成**回合级禁止标志**（`compressIneffectiveThisTurn`），本意止血「每轮空转」，但对**模型自助长任务**是错的——一个回合可跑几十轮工具，中途上下文增长、旧组滑出保留区后又有可压内容，却被标志挡住，该回合后半段失去压缩保护。改为「事前收益门槛 + 事后如实提示」，**不设任何回合级禁止标志**。

**事前（收益门槛，`AgentLoop` / `SubAgentLoop` 触发点）**：

```java
if (contextManager != null && contextManager.shouldCompress(messages)) {
    long compressible = contextManager.compressibleTokens(messages);   // 本次能压掉的 token 量（take 组合计，纯估算）
    boolean forced = contextManager.estimate(messages) >= max × FORCE_COMPRESS_RATIO;  // 危险区
    if (compressible >= max × MIN_COMPRESSIBLE_RATIO || forced) {
        压缩（一次 LLM 调用，带重试）→ 见事后
    } else {
        跳过本次（不调 LLM、不设禁止标志）；若本回合尚未提示过 → 提示一次（见下）
    }
}
```

**事后（压缩结果复核）**：

| 结果 | 判定 | 动作 |
|---|---|---|
| `OK` 且压后 `estimate < 阈值` | 有效 | 提示「自动压缩已完成，上下文降低至 X%」（既有文案） |
| `OK` 且压后仍 `≥ 阈值` | 压不动（保留区保底 1 组自身超预算，或常驻内容过大） | 提示「自动压缩后上下文仍占 X%（大输出占满保留区）；有新内容可压时自动重试」 |
| `NOTHING`（`take = 0`） | 无旧组可压（常驻内容/最近对话占满；通常已被事前门槛拦下） | 不重复提示（事前已提示） |
| `FAILED` | 失败/中断 | 维持既有：主代理中止本轮并 onError；子代理中止并返回失败文本 |

**关键性质（消除「第二次压缩不了」）**：

- 事前门槛只跳过**本次**；任务继续推进 → 旧组不断滑出保留区 → `compressibleTokens` 自然增长 → **随时可再次压缩**（长任务回合可压缩多次）；
- 危险区（`estimate ≥ 0.85×max`）**无条件压缩**，避免贴近窗口导致请求报错；
- 提示去重：`AgentLoop` 用 `ineffectiveWarnedThisTurn`（回合内一次，`runUserTurn` 开头重置）；`SubAgentLoop` 用 `ineffectiveWarned`（子代理全程一次，经 `onSubAgentNotice`）。**该标志只控制提示，不阻塞压缩**；
- 手动 `/compact` 不受任何门槛限制（保持既有语义：手动压缩总可尝试，结果为「暂无可压缩」由既有文案呈现）。

文案定稿：

- 事前跳过：「自动压缩暂缓：可压内容不足（最近内容与常驻提示词已占 X%）；有新内容可压时自动重试」
- 事后仍超阈值：「自动压缩后上下文仍占 X%（大输出占满保留区）；有新内容可压时自动重试」
- 子代理差异（有意）：事后提示文案为「压缩后上下文仍占 X%（大输出占满保留区）；有新内容可压时自动重试」——**无「自动」前缀**（提示走【子代理N】通道，无需再声明"自动"），且「暂缓/仍占」两类提示**共享同一「全程一次」的提示额度**（`ineffectiveWarned`）：任一先到即占额度，另一类不再重复提示。

### 2.5 兼容与影响

- `chunkGroups`、摘要生成、重试/中断链路（`ContextCompressor`）、pinned/system 豁免规则**均不变**；
- `ContextManager` 新增公开方法 `compressibleTokens(List<Message>)`（＝ `take` 对应组的 token 合计，纯估算；`take`/`keepCount` 复用同一套分组结果）；
- 子代理与主代理共用 `ContextManager` → 自动同享新算法；`SubAgentLoop` 仅需把 v1 的 `compressIneffective` 换成 v2 的事前门槛判定 + 提示去重（不阻塞压缩）；
- **v1 已实施内容的改造清单**（本次一并改）：
  1. `AgentLoop`：`compressIneffectiveThisTurn`（回合级禁止标志）→ 改名 `ineffectiveWarnedThisTurn`，**仅控制提示去重**；循环顶条件去掉该标志，改为「事前可压量门槛 + 危险区豁免」；提示文案按 2.4 定稿；
  2. `SubAgentLoop`：`compressIneffective` → `ineffectiveWarned`（子代理全程一次提示），同上不阻塞压缩；
  3. 既有测试中"压缩后仍超阈值"的场景改为断言事前跳过（**不调压缩 LLM**，`completeChatRequests == 0`）与提示文案。
- 旧会话无迁移问题（压缩是运行时行为，历史消息格式不变）；
- 设置窗/GUI 不需要变化（百分比展示来自 `estimate/max`）。

## 3. 测试计划

### 3.1 `ContextManagerTest`（按新语义重写，替换锁定「硬留 6 组」的用例）

1. 常量语义：`KEEP_BUDGET_RATIO = 0.2`、`KEEP_MIN_GROUPS = 1`、`MIN_COMPRESSIBLE_RATIO = 0.05`、`FORCE_COMPRESS_RATIO = 0.85`；测试不再引用已删除的 `KEEP_RECENT_GROUPS`/`COMPRESS_RATIO`（原锁定「硬留 6 组」的用例按上述语义重写）；
2. **保留区预算内尽量多留**：构造若干小组，使预算能容纳全部 → `take = 0`、返回同一引用、不调 LLM；
3. **超预算压掉早期组**：预算容纳最近 K 组 → 断言压缩后保留的组恰为最近 K 组（组内容可比对）+ 摘要置前；
4. **保底 1 组**：最新组自身 > 预算 → 压缩后仍保留该组（`take = 组数 − 1`）；
5. **`compressibleTokens`**：等于 `take` 对应组合计；`take = 0` 时返回 0；与 `compress` 的实际被压组一致（同一分组结果）；
6. **配对不破**：保留边界落在工具组上时，`assistant(tool_calls)` 与其 tool 结果同留或同压（沿用原 `chunkGroups` 用例 + 组边界用例）；
7. `pinned`/`system`/既有 `summary` 规则不变（沿用既有用例）。

### 3.2 `AgentLoopCompactTest`

1. **事故场景回归（新增）**：`max = 200000`（阈值 130k、保留预算 26k），预置 6 个各约 25k token 的组（模拟保留区装满大输出）→ 一次压缩后 `estimate < 阈值`，警告为「自动压缩已完成，上下文降低至 X%」，**不含**「仍占」；
2. **可压量不足 → 事前跳过（调整既有用例）**：`max = 50`（阈值 32.5、门槛 2.5、保留预算 6.5），本轮用户输入本身即 ≈64 token（超阈值且可压量 0）→ **不调压缩 LLM**（`completeChatRequests == 0`）+ 提示「自动压缩暂缓」一次；
3. **长任务回合可多次压缩（新增，核心回归）**：`max = 200000` 级别场景，脚本模拟多轮工具调用使可压量逐轮增长（旧组滑出保留区）→ 断言 `completeChatRequests ≥ 2`（长任务回合不被"只能用一次"卡死）；
4. **危险区豁免（新增）**：`estimate ≥ 0.85×max` 且可压量 < 门槛 → 仍发起压缩（`completeChatRequests == 1`）；
5. **提示每回合最多一次（新增）**：连续多轮触发"暂缓" → 「自动压缩暂缓」提示只出现一次；
6. 既有用例（压缩成功文案/压缩指示器事件/手动 `compactNow` 不受门槛限制等）保持通过或按新语义微调。

## 4. 风险与取舍

| 风险 | 说明 | 缓解 |
|---|---|---|
| 压缩更激进、近期细节进入摘要 | 保留区从「固定 6 组」变为「≤0.13×max」，大组场景下保留内容变少 | 摘要合并旧摘要且 ≤5000 字；用户可在关键节点手动 `/compact`；后续可评估「保留区预算比例」调参 |
| 组仍不可拆（超大组） | 最新 1 组自身超阈值时可压量长期不足 | 事前门槛跳过（无 LLM 空转）+ 事后如实提示 + 危险区强制压缩保命；组内折叠列为后续备选 |
| 小组很多时保留过多组 | 无组数上限，预算内可能保留几十组 | 预算硬约束（≤0.13×max），总量可控；组多但小对模型无负担 |
| 门槛跳过导致贴窗报错 | 可压量不足且未达危险区时跳过压缩 | 危险区豁免（≥0.85×max 无条件压缩）；服务端报错仍有既有重试/报错链路兜底 |
| 摘要净增（被压内容 < 摘要输出） | 可压量门槛（5%×max，200k→10k ≫ 摘要 ~3.5k）已覆盖 | 门槛即为此设；小窗口模型下门槛较小，仍有危险区豁免与摘要上限约束 |

## 5. 验收标准

1. 事故场景（6 组大输出，总 ≈150k token，max 200k）：一次压缩后占用 < 65% 阈值，提示「降低至 X%」；
2. 可压量不足（保底 1 组超预算）：**不调压缩 LLM**，提示「自动压缩暂缓」一次，任务继续；
3. 长任务回合：随任务推进可多次压缩（`completeChatRequests ≥ 2`），不被"只能用一次"卡死；
4. 危险区（≥85%×max）：即使可压量不足也强制压缩一次；
5. 子代理同享以上行为（提示走子代理通道，全程一次）；
6. `mvn test` 全绿，无回归。
