# 瞬时错误长重试增强（429/500/502）设计

日期：2026-08-27
状态：已批准（三节设计均获确认）

## 背景与问题

公司内网环境 LLM API 调用成功率低，平均 5~10 次才能成功一次，错误集中在 **429（限流）、500（服务端报错）、502（网关报错）**。现有代码只对 429 做长重试（2s 起步 +2s 递增、上限 10s、总时长 30 分钟）；500/502 只快速重试 1 次即报错，严重影响软件可用性与稳定性。

## 需求

1. 429、500、502 均进入长重试：**固定 5 秒一次，持续最多 20 分钟**；其他错误（网络/超时/503 等）维持现状
2. 子 agent 同样处理；主、子 agent 重试互不影响
3. 流式消息成功返回时（首个增量到达）"重试中"文案立即消失，恢复常规轮换模式
4. 文案格式：
   - 正常：`正在加载中...` 与 `可随时补充信息...` 两个随机轮换（现状已满足）
   - 报错时：基础文案 + 后缀，基础文案进入重试态时随机取一条并**冻结**
     - `正在加载中...(429限流，重试第x次)`
     - `正在加载中...(500服务报错，重试第x次{具体服务返回的报错json})`
     - `可随时补充信息...(502网关报错，重试第x次{具体服务返回的报错json})`
   - 429 明确是限流，**不显示**错误体；500/502 **显示**服务返回的错误体

## 已确认的边界

- 长重试仅覆盖 **429、500、502** 三个状态码；其他 5xx（503/504 等）维持现状（快速重试 1 次后报错）
- 网络错误（NETWORK/TIMEOUT）不纳入长重试，维持现状
- 重试期间基础文案冻结（用户确认：取实现更简单的方案）

## 设计

### 1. RetryPolicy（core/agent/RetryPolicy.java）

- 工厂方法 `rateLimit()` 更名 `transientErrors()`：`new RetryPolicy(5000, 0, 5000, 20 * 60 * 1000L)`
  - `incrementMs = 0` 使 `delayMs()` 恒为 5000（固定 5s/次）
  - `maxTotalMs = 20 分钟`，最多约 240 次
- 类注释更新为"瞬时错误长重试（429/500/502）"
- 算法（delayMs/isExhausted）与字段不动；测试仍可小参数覆写

### 2. LlmException（core/llm/LlmException.java）

- 新增字段：
  - `public final int httpCode`（非 HTTP 错误为 0）
  - `public final String body`（原始响应体，可 null）
- 现有构造器保留（默认 httpCode=0、body=null），DeepSeekClient 中其他 `new LlmException(...)` 调用点零改动
- `of(int httpCode, String body)` 填充两个字段

### 3. AgentLoop / SubAgentLoop 长重试条件

- 条件从 `e.type == LlmException.Type.RATE_LIMIT` 扩展为：
  `e.type == RATE_LIMIT || e.httpCode == 500 || e.httpCode == 502`
- 重试循环内遇非目标错误（503/网络等）：维持现状——break 退出重试态、复位指示器、onError 提示
- 超时总结文案按最后错误码区分前缀：
  - 主循环：`429 重试了 N 次，持续 X 分钟仍失败，已停止重试`（500/502 前缀同理）
  - 子 agent：加 `子 agent ` 前缀

### 4. 流式返回即复位指示器

- 循环内新增 `boolean[] inRetry` 标志（handler 为复用对象，须用可变容器）；进入重试循环时置 true
- handler 回调：
  - `onContent` / `onThinking` 首个增量到达且 inRetry → 置 false 并 `ui.onRetryProgress(RetryProgress.none())`，指示器立即恢复轮换
  - `onFinish` 兜底复位：重试成功但零增量（如纯 tool_calls 回复）时同样退出重试态
  - `onError` 不复位（由重试循环或统一复位兜底）
- 循环正常结束的 `onRetryProgress(none())` 保留（幂等兜底）

### 5. RetryProgress 值对象（新类，core/agent/ 与 RetryPolicy 同包）

- 不可变：`attempt`（0=复位）、`httpCode`、`body`
- 静态工厂：`of(int attempt, int httpCode, String body)`、`none()`
- 使重试进度穿透 5 层接线只传一个对象，接口签名稳定

### 6. 接线签名变更

| 位置 | 变更 |
|---|---|
| AgentUi.onRetryProgress | `int attempt` → `RetryProgress p` |
| SessionController.retryStateListener | 类型同步为 `(RetryProgress) -> void` |
| SessionManager 会话级监听器 | `onRetryProgress(SessionHandle h, RetryProgress p)` |
| MainWindow | 转发至 `runningIndicator.setRetryProgress(p)` |
| RecordingUi（测试） | 签名同步 |

### 7. RunningIndicator 文案

- 删除 `RETRY_TEXT_PREFIX` 常量，新增纯静态方法 `retryText(RetryProgress p, String base)`（可单测）：
  - `base + "(" + 错误码标签 + "，重试第" + attempt + "次" + 错误体 + ")"`
  - 错误码标签：429→`429限流`、500→`500服务报错`、502→`502网关报错`、其他→`HTTP xxx`（防御性）
  - 错误体：仅 500/502 且 body 非空时追加，**截断 200 字符**；429 或无 body 时省略
  - 重试次数时序：每次尝试发起前立即更新指示器（`attempts++` → 更新 `重试第N次` → 等待 5s → 发起尝试），等待与尝试期间均显示本次尝试次数——用户看到错误后立即看到重试进度
- 状态字段 `retryAttempt` 替换为 `retryBase`（冻结的基础文案）
  - `setRetryProgress(p)`：
    - `p.attempt == 0` → 恢复轮换（`displayText` + `startRotateText`）
    - `p.attempt >= 1` 首次进入 → `retryBase = pickText(rnd)` 冻结、停轮换；后续每次更新后缀（错误码/错误体随最近一次失败更新）

### 8. 主/子 agent 互不影响

主、子 agent 各自持有独立的重试循环与 inRetry 标志，互不读写对方状态。子 agent 运行期间主循环阻塞等待其结果，指示器按各自进度更新，子 agent 结束时 `none()` 复位不影响主循环后续状态（现状已如此，本次仅同步签名）。

## 错误提示汇总

| 场景 | 文案 |
|---|---|
| 指示器（正常轮换） | 正在加载中... / 可随时补充信息...（10s 随机轮换） |
| 指示器（429 重试中） | `正在加载中...(429限流，重试第N次)` |
| 指示器（500 重试中） | `正在加载中...(500服务报错，重试第N次{body前200字符})` |
| 指示器（502 重试中） | `可随时补充信息...(502网关报错，重试第N次{body前200字符})` |
| 重试超时（主循环） | `429 重试了 N 次，持续 X 分钟仍失败，已停止重试`（500/502 前缀同理） |
| 重试超时（子 agent） | `子 agent 429 重试了 N 次，持续 X 分钟仍失败，已停止重试` |

## 范围外（不做）

- 网络错误（NETWORK/TIMEOUT）长重试
- 503/504 等其他 5xx 长重试
- 流式中途（SSE 已开始后）错误重试——HTTP 状态码错误在流开始前抛出（DeepSeekClient:138），中途断流归为 NETWORK/TIMEOUT，不在本次范围
- 重试逻辑重构为独立组件
